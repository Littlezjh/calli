## 额度现状

改造前，`QuotaBoard` 是自带 scrim 的弹窗。每个 agent 一行，每种周期一列；模型组会增加子行。读取使用 daemon 缓存，每分钟重读，手动刷新才要求重新查询。失败时保留上次读数，已有点击展开周期详情的能力。这些已有行为应保留。

主要不足：

1. 配置入口虽然统一，额度仍打开另一层弹窗，与新版页面返回关系不一致。
2. 手机需要容纳全部周期列，账号、套餐、百分比、更新时间和重置时间竞争同一行空间。
3. 单元格可见文字只有百分比，虽然无障碍标签写了“剩余”，视觉上仍需要判断方向；简写时间也没有持续写明“重置”。
4. `windows=[]`、首次未读、失败且无缓存等状态的信息组织不够明确；有旧读数时，应直接提示读数时间，避免当成实时数据。
5. 较低额度和模型繁忙是不同信号；不能用繁忙程度替代额度，重要异常不能藏在 `+N` 后面。

## Playground 方向

- **A 紧凑列表（推荐）**：每个账号一行，概况显示剩余最少的周期、明确的“剩余”和同一周期的重置时间。有多个低额度周期时直接标出数量；点击进入全部周期详情。
- **B 账号卡片**：桌面两列，手机单列；每张卡先显示两个最紧的周期。较直观，但账号较多时滚动更长。
- **C 周期对照**：桌面按周期列对齐；手机转成带周期标签的账号行，避免整张横向表挤进屏幕。

顶部切换方案、设备、主题；下方只渲染当前方案的完整页面。保留现状结构示意，详情统一整页进入／返回，避免面板内再次包圆角导航条。玻璃只用于独立返回和刷新按钮，正文保持实色。选择按钮写入临时服务的选择记录。

交互包括筛选、搜索、账号详情、返回、查询／重试、主题／设备切换。后续补充了聊天场景：输入框底部的额度快览、账号选择器中分别操作账号与额度、查看全部额度后返回聊天，以及草稿／阅读位置保留。数据为虚构场景；刷新只模拟结果，不接触真实账号、会话或配置。

## 数据与实施边界

### 聊天入口与完整页面

补充核对：聊天状态面板的“查看额度”、斜杠 `/usage` 和配置里的额度入口，目前已经打开同一个 `QuotaBoard`。聊天账号选择器旁的额度概况由 `AgentQuota` 单独渲染，两者共用 `Api.agentQuota`、请求去重和缓存，但各自维护读取状态与详情呈现。

本轮一起统一这两个使用场景：聊天保留紧凑概况和就地快览，不为检查一个重置时间打断聊天；“查看全部额度”进入统一配置页，并将当前账号置顶；账号详情作为下一级页面进入。完整页面返回时恢复聊天草稿与阅读位置。点击额度详情不能选择或切换账号。

概况、快览、完整页面应复用周期命名、剩余量、重置时间和异常状态规则；共享数据更新，避免手动刷新后另一个入口仍停留在旧显示。不同入口按需要加载，不因聊天内展示一个账号而读取全量账号或历史趋势。Playground 已补充聊天内入口，并用同一份模拟状态演示三处同步；真实 `AgentQuota`、聊天输入框快览和 `QuotaBoard` 已接入同一个 `quota-reading` 状态。每个 API 客户端／账号只有一个挂载期间的轮询与请求，手动刷新同步发布给所有订阅界面；新机器使用独立客户端，不沿用旧机器读数。

当前 `PlanQuota` 只有 `windows`（周期、可选模型范围、已用百分比、可选重置时间／负载）、可选套餐／备注，以及读取时间。先充分利用这些字段，不新增预测数据：

- 不相加或平均不同账号、周期、模型池的百分比。
- 不推算“还能发多少消息”“还能用几小时”；没有消费历史支持这样的结论。
- 首屏读概况；如未来增加历史趋势，只在进入详情时读取和构建。
- 成功读数为 0% 才显示耗尽；未知、尚未加载、失败且无缓存、失败但有旧值、成功但无额度信息分别处理。
- 查询／查看详情与选择会话账号分离，不因点额度而切换账号。
- 额度新页继续使用 capabilities 和统一数据结构，不按 agent 名字在生产前端分支。
- 全部周期继续支持模型繁忙与服务备注；Playground 重点比较承载布局，不将未展示的字段从生产实现删除。

本轮接入配置子路由、状态面板、`/usage`、聊天快览和账号选择器的额度入口。从聊天直接进入额度时，手机在列表顶层返回会直接回到原聊天；从配置目录进入则逐级返回目录。归档、导入历史也已转为页面；资源长表单按清单继续统一。登录和确认类短弹窗保留。
