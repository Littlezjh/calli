> 实现更新：内置扩展宿主、独立外部工作数据源和 LoopX 首版已落地。本文保留原设计与后续能力；当前接口、兼容范围及验证限制以 [LoopX 接入记录](loopx-integration.md) 为准。


状态：设计稿，未实现。本文用「看板」这个真实需求，检验 [Limi 扩展机制](extensions-design.md) 能不能既保持简洁好看，又让看板、LoopX 这类工具真正接进来。愿景见 [VISION.md](VISION.md)，可点击的界面草图见 [design/extension-workbench.html](design/extension-workbench.html)（演示用，没有真实接口）。

依据的现有设计和代码：

- 页面一次只连一台机器（`packages/web/src/main.tsx`）。

## 结论先说

1. **看板做成第一个内置 Limi 扩展。** 走公开契约实现，不直接加进核心，用它验证宿主的插槽、原语、快照和订阅。行为沿用 `board-tags-design.md` 已定的规则。
2. **先做只读的线程执行看板，再接结构化步骤和 LoopX。** 不靠猜测任务状态来假装看板是完整的。
3. **看板是视图扩展，LoopX 是工作数据源扩展。** 两者通过宿主里一个很小的声明式「工作投影」连接，会话摘要和详情也读这一份；不开放任意 React，看板也不依赖 LoopX 的包。
4. **用看板验证界面契约，用 LoopX 验证数据源契约。** BotMux 可以并行验证通知出口，三种集成分别检验扩展的一部分能力。

## 用户流程

**启用和入口。** 「配置 → 扩展」只负责管理：启用、停用、设置、查看权限。看板启用后，侧栏「计划」旁边多一行「看板」，可以固定或取消固定；点开后，主区域换成看板，地址 `#/board`。手机上同样是侧栏的一行，点开占满主区域。

**看什么。** 列沿用看板设计：待处理（等审批、等回答、出错、有新结果没看）、运行中、空闲。卡片是线程，正面只放一眼要看到的：

- 标题、agent 实例、运行状态（运行中、等审批、等回答、出错、空闲）；
- 步骤：「3/7 · agent 报告」，或「未报告步骤」；
- 关联的计划项（如有）；
- 最近活动时间（线程已有的 `updatedAt`）。线程很久没有新事件只是空闲，不算过时；只有订阅断开或同步失败时，才显示「可能已过时」。

**进入线程和详情。** 整张卡片点击进入对应的线程；卡片上另有一个「详情」按钮，打开右侧面板（手机上全屏），这是 M2 的内容：步骤列表并标明来源、最近的活动、关联的计划项，以及「打开会话」。

**在会话里。** 输入框上方只有一行摘要，多个扩展聚合在这一行里，点开再看详情。每个扩展不各自加一排按钮。

**有 LoopX 时。** 卡片多一行「LoopX · 目标 · 待办 2/5 · 来源 LoopX · 10 分钟前」，会话摘要和详情里显示的是同一份状态。

## 三种状态，分开显示

| 状态 | 回答的问题 | 来源 | 可靠程度 | 归谁管 |
| --- | --- | --- | --- | --- |
| 运行状态 | 线程现在在干什么：运行、等审批、等回答、出错、空闲 | 核心的统一事件 | 连接正常时的观测值；断线标明未知或过期 | 核心 |
| 步骤计划 | agent 说它打算做哪几步、做到哪了 | agent 报告的 `plan.updated` | agent 自报，不代表任务已验收 | agent |
| 业务完成 | 这件事做完、验收了没有 | Limi 计划项由用户勾选；外部工具（如 LoopX）有自己的状态 | 以所有者为准 | 计划项归 Limi 核心；LoopX 的状态归 LoopX |

规则：

- 一轮结束（`turn.done`）不等于任务完成；归档也不等于完成。
- 没报告步骤就显示「未报告」，不是 0%。
- 暂停、失败、等待、离线，各自如实显示，不合并成「未完成」。
- 每个状态都带来源和各自的更新时间（运行状态、步骤计划、外部来源分别记录）。拿不到的显示「未知」。新鲜度按订阅是否正常、最近一次同步成功的时间判定，不按闲置时间：线程长时间没写事件，不代表数据过期。
- 一个任务可以关联多个线程、多个实例：计划项通过 `todo_threads` 关联线程。LoopX 里登记的 agent id 不等于 Limi 的实例 id；LoopX 目标和 Limi 线程的关联必须显式写明机器、来源里的目标、线程，可以一对多，不靠同一个目录去猜。
- 看板只投影，不另存一份。计划项不建第二套存储，完成仍由用户在计划页勾选；在看板上勾选，调用的也是同一个核心操作。

看板因此有两种视角：

- **线程执行**（首版）：卡片是线程，只从线程摘要和运行状态画出，不需要任何任务数据。
- **业务任务**（后续）：按计划项或 LoopX 目标分组，每组标明数据来自谁（Limi 计划项，或 LoopX）。LoopX 自己规定完成要有写回、证据和终审，它的状态以 LoopX 为准。

## 看板扩展的最小契约（草案）

| 部分 | 内容 |
| --- | --- |
| 快照和订阅 | 先订阅并缓冲变化，再取快照；快照带 revision 或水位，用来和订阅衔接：早于快照的变化丢弃，晚于快照的照常应用。队列溢出、断线或扩展重启时，作废并重新读快照，不回放历史。晚返回的旧快照不能覆盖更新的状态 |
| 关联标识 | 机器、线程、轮次、计划项 id，以及外部工具自己的 id（例如 LoopX 的目标 id），都标明来源 |
| 结构化进度 | 来源；性质（agent 报告、已核实、未知）；已完成数和总数（可能没有）；条目；更新时间；是否可能过时 |
| 活动 | 时间、类型（开始一轮、等审批、出错、结束一轮等）、来源；只给元数据，不给对话内容 |
| 宿主绘制的视图 | `board`、`list`、`detail`、`threadSummary` 四种，扩展只提供数据，样式由宿主决定 |
| 列的归属 | 用宿主提供的注意力摘要（一个纯函数接口）判定，和侧栏「按活动查看」同一套；看板不 import `packages/web/src/sidebar.ts` 之类的核心私有模块 |
| 受控动作 | 打开会话、打开只读文件查看器、在计划项上勾选（用户点击，走核心已有操作）、打开外部工具自己的界面链接 |

不为看板开放的：原始工具调用流、整段对话、思考内容。步骤计划的文字、LoopX 目标和待办的文字，都属于内容，不放进默认的元数据权限。「读进度」允许读取指定线程的步骤快照，再加一个只说明「哪个线程的计划变了」的受限通知；「读工作数据源」另按来源与关联线程授权，见下。要显示「精确到哪一步」，来源必须可核实；agent 自报的步骤只能标「agent 报告」。

**视图要能注册，不是在 App 里加分支。** 现在的主视图和侧栏入口都是写死的。扩展的工作视图需要通用的注册方式：扩展声明一个视图，宿主负责路由（例如 `#/ext/<id>/<view>`，看板沿用 `#/board`）和侧栏的固定入口。不为每个扩展在 `App.tsx` 里加分支。

## 工作投影：连接数据源和视图（草案）

只有 `ui.page`、`ui.threadStatus` 这类插槽，还不够让多个扩展共享同一份工作进度：每个扩展各画各的，看板也读不到 LoopX 的状态，除非直接依赖它。所以在宿主里加一个很小的声明式「工作投影」契约，而不是开放任意 React：

- **两种扩展各管一头。** 看板是「视图扩展」，只负责展示；LoopX 是「工作数据源扩展」，负责提供工作项，将来可能有受控动作。两者都只和宿主的投影打交道，看板不 import LoopX 的包。会话摘要和详情面板也读同一份投影。
- **数据源拥有真相。** 宿主只缓存投影，以及工作项和线程之间的显式关联；不改写、不合并数据源的状态。来源标签由宿主加，扩展不能自称别的来源。
- **声明方式（名称是草案）。** 数据源在清单里声明 `provides.workSources`，视图在清单里声明 `contributes.views`。数据源提供 `snapshot`，状态变化时发 `changed` 或 `invalidate`，由宿主重新取快照。

一个工作项在投影里包含：

| 字段 | 含义 |
| --- | --- |
| 来源 id、工作项 id | 由宿主加上来源；同一来源内 id 稳定 |
| revision | 数据源给出的版本，宿主据此丢弃过时的更新；只在同一来源内比较，不同来源的 revision 互不可比 |
| 范围 | 机器，以及显式关联的线程（可以是多个） |
| 更新时间、观察时间 | 数据源最后更新的时间（`updatedAt`），以及宿主最后成功取到的时间（`observedAt`） |
| 新鲜度 | 新、可能已过时、未知；按订阅是否正常和最近一次同步成功的时间判定，不按工作项闲置多久 |
| 业务状态 | 由数据源给出，例如未开始、进行中、等你决定、已完成待验收、已验收；不由宿主推断 |
| 运行标记 | 由宿主根据关联线程的运行状态加上（运行中、等审批、出错……），不由数据源声明 |
| 完成依据 | 谁、凭什么判定完成：用户勾选、LoopX 的证据和终审、agent 自报 |

版本只在同一来源、同一作用域和宿主代次内比较。来源能提供单调版本时使用该版本；只有不透明版本或没有版本时，宿主串行刷新并用请求代次丢弃旧响应，不能把时间戳或版本字符串的字典顺序当作先后。任务被来源删除或移出授权范围时，快照必须移除对应投影；停用来源后标记不可用，不继续显示为实时数据。

**首批来源只有两个，用来验证字段：** Limi 计划项（内置来源，读现有的 `TodoRecord` 和 `todo_threads`，不另存）和 LoopX。不做通用工作流引擎。

**agent 报告的步骤不是工作项。** 现在的计划条目只有文字和状态，没有稳定的步骤 id；agent 重新规划时，宿主整体替换这个线程的步骤快照，不按文字去匹配旧步骤。时间线里计划的 `done`（`packages/web/src/timeline.ts:405`）只表示这一轮结束了，不代表所有步骤都已完成。

**权限不因启用看板而扩大。** 视图扩展消费某个来源的工作项，需要用户授权它读这个来源，并且只能看到它有权看的线程上的工作项。启用一个看板，不等于拿到所有来源、所有线程的内容。

首版取两者的交集：来源已授权，关联线程也在授权范围内，宿主才发布工作项。未关联的计划项仍留在原计划页；跨线程之外的目标浏览范围以后单独设计。计划项勾选也不是读取权限的一部分：M3 增加限定计划项 id 和完成值的宿主动作，绑定本次用户点击、复核权限、调用已有核心更新；不开放任意写入或让扩展自行声明「用户已点击」。

## LoopX 怎么接

- **谁执行，谁展示。** 长程由 agent 的原生循环执行（按 [LoopX README](https://github.com/loopx-project/loopx) 的描述：Codex `/goal`、Claude `/loop`、pi 的 goal 扩展），LoopX 记录目标、待办、关卡和证据，并且有自己的个人工作区、浏览器和 PWA 界面；它的看板只是投影，状态以 LoopX 为准。Limi 只在线程旁边展示这份状态，并链接到 LoopX 自己的界面。原生循环优先。
- **同一份状态，三处展示。** LoopX 扩展读出的状态，同时用于会话摘要、看板卡片和详情面板，不各自计算。
- **观察和推进分开。** 本文只做观察。暂停、续轮等操作，要等 CLI 行为核实后再设计，不根据样例命令作承诺。
- **已核对的源码（只读，没有运行）。** 在 [LoopX 固定版本 aa7d44e](https://github.com/loopx-project/loopx/tree/aa7d44eb6206bba39c216a9727c3a26a325ef0d1) 中：`loopx/cli_commands/status_registration.py` 的 `status` 命令有格式选项，以及 `goal-id`、`agent-id`、`include-task-graph`、`projection-cache` 等参数；`status.py` 的 `handle_status_command` 汇总状态，支持待处理队列、运行历史、agent 分道和格式化输出；`todo_list.py` 有 JSON 输出，但同时会追加一条待办的 rollout 事件，大列表的 JSON 还可能走另一条结果通道。所以结构化输出有源码依据，但不能把所有查询都当作没有副作用。
- **候选的读取命令：** `loopx status --format json --goal-id <id>`。依据是 [`loopx/cli_runtime.py`](https://github.com/loopx-project/loopx/blob/aa7d44eb6206bba39c216a9727c3a26a325ef0d1/loopx/cli_runtime.py)：`add_subcommand_format`（第 106 行）提供 `--format {markdown,json}`；`print_payload`（第 91 行）用 `json.dumps` 输出 JSON，并且在输出前先调用 `usage_ping.capture_result`。这条命令没有实际运行过，需要注意三点：
  - `status` 默认读全局注册表，不限于当前目录，必须明确用 `--goal-id` 过滤；
  - 查询路径上有统计、缓存等可能的副作用，接入测试时要确认并在清单里声明；
  - 待办列表的 JSON 可能被截断或分页，返回的条数不能当作总数。
- **仍待集成测试：** 实际安装版本的完整字段、截断、读取时的副作用和权限范围；在 Limi 里调用 CLI 是否正常；LoopX 目标和 Limi 线程的显式关联怎么建立；待决定事项、暂停的真实语义。

外部界面链接需要配置并验证从用户设备可访问的地址与鉴权方式；不能把远程主机的 `127.0.0.1` 地址直接发给手机。未配置时只显示 Limi 内的状态，外部完整界面入口标为未配置，不默认开放代理或端口。

## 扩展能做什么

| 范围 | 能做什么 | 例子 | 首版 |
| --- | --- | --- | --- |
| 观察 | 读白名单里的线程状态和事件；进度内容单独授权 | 看板、BotMux | 线程元数据在 M1，步骤在 M2 |
| 展示 | 在宿主插槽里提供数据，由宿主绘制 | 看板、LoopX 摘要 | 是 |
| 操作 | 用户点击触发的受控动作 | 打开会话、勾选计划项 | M1 只打开，M3 再加入限定计划项的勾选动作 |
| 驱动 | 自动发起下一轮 | Hub 驱动的续轮 | 否 |
| agent 资源 | 查看和安装 skills、MCP 等 | 技能页、MCP 页 | 走核心现有入口，不经扩展 |

**原语**：状态文字和色调、进度（标明来源）、标记、清单、表格、键值对、时间、链接、操作按钮。

**插槽**：侧栏导航项、主区域工作视图、详情面板、会话里的一行摘要、线程标记、设置。

复杂的工具可以放一个链接，打开它自己完整的界面（例如 LoopX 的看板）。首版不接受扩展自带的 DOM 或 CSS。

**多个扩展同时启用时怎么保持好看：**

- 会话摘要始终只有一行，多个扩展合在一起，点开再分开看；
- 侧栏导航项只显示用户固定的那几个，其余收进「更多」；
- 看板卡片上的信息总量由宿主限制：默认最多一行扩展摘要，多个扩展聚合在这一行里，其余折叠进详情；装了十个扩展，卡片也不会多出十行；
- 所有内容都用同一套原语和样式变量绘制，没有扩展自定义的颜色。

## 开发、存放、发布、安装

- **清单。** 包括 `id`、名称、版本、`apiVersion`、入口（构建产物里的路径）、权限、贡献点（用到哪些插槽），以及依赖检测。
- **首个看板。** 放在本仓库，作为独立 package（例如 `packages/ext-board`），只依赖公开的契约包（例如 `packages/extension-api`），不 import web 或 daemon 的内部模块；同在一个仓库也只能走公开契约，列的判定也通过宿主接口取得。这样能证明契约本身够用。
- **社区扩展。** 各自放在独立仓库。Git 仓库只是源代码的载体，不是运行时：安装的是固定版本的构建产物，并校验完整性；不在用户机器上直接执行仓库里的脚本。
- **安装和启停。** 先支持从本地路径或固定的地址安装；按机器启用；安装和升级时显示权限，新增权限需要重新确认；升级失败可以回到上一个版本。
- **不做市场。** 发现页和社区分发等真的有多个扩展时再做。

## 当前设计的缺口

- 没有跨线程的「任务」实体，只有计划项和线程的多对多关联。看板以线程为卡片，可以绕开这个问题，但「一个任务的整体进度」暂时无法表达。
- 看板只能看当前连接的那台机器；跨机器的看板要等多机器设计。
- 步骤计划只能标「agent 报告」，各家 agent 报不报、报得多细，需要逐家核实。
- 线程已有 `updatedAt`，但运行状态、步骤计划、外部来源各自的更新时间，宿主的 `observedAt`，以及断线后的新鲜度判定都还没有。
- 线程深链、权限投影后的线程摘要、宿主的插槽和原语，都还不存在。
- 主视图和侧栏入口是写死的，需要通用的视图注册和宿主路由。
- 现有的 `ui.*` 插槽只能让扩展各画各的，没法共享工作进度；需要工作投影契约。
- 全局流不含 `plan.updated`，最新计划需要宿主提供快照和受限的变更通知。
- LoopX 的目标和 Limi 线程如何关联，不清楚。

## 里程碑

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| M0 前提 | 按白名单投影的线程摘要；宿主的注意力摘要接口（等审批、等回答、出错，和侧栏共用）；通用的视图注册、宿主路由和侧栏固定入口；`board`、`list` 两种原语 | 只读摘要里没有对话内容；新增视图不需要改 `App.tsx` 的分支；侧栏和看板的判定一致 |
| M1 只读线程执行看板 | 契约包；`packages/ext-board` 作为内置视图扩展，只用线程摘要和注意力摘要；侧栏入口和主区域视图；整张卡片点击进入线程 | 不启用时界面和现在完全一样；三列判定正确；看板不 import 核心私有模块；桌面和手机、亮色和深色都看过 |
| M2 步骤、详情和会话摘要 | 「读进度」权限下每个线程最新计划的快照（整体替换）和变更通知；详情面板和 `detail` 原语；会话里的一行摘要 | 没有「读进度」权限时拿不到计划文字；未报告步骤显示「未报告」；重新规划后不残留旧步骤 |
| M3 工作投影和计划项来源 | 工作投影契约（含快照和订阅的衔接）；Limi 计划项作为内置来源；卡片显示关联的计划项；在看板上勾选计划项 | 勾选结果和计划页一致，没有第二份数据；晚到的旧快照不覆盖新状态；看板不 import 任何数据源的包 |
| M4 LoopX 数据源（只读） | 集成测试通过后，LoopX 作为工作数据源接入投影；会话摘要、卡片、详情读同一份；关联显式写明机器、目标、线程；附上打开 LoopX 自己界面的链接 | 来源和更新时间都显示；拿不到时显示「未知」；读取的副作用已核实；不提供暂停、续轮 |
| M5 BotMux 最小提醒 | 按 `extensions-design.md` 的首版范围实现，可以和 M1 并行 | 沿用该文档的验收 |
| M6 外部扩展安装 | 从本地路径或固定版本安装；权限确认；按机器启停；升级和回退 | 不执行仓库脚本；新增权限要重新确认 |

Hub 驱动的续轮、新建线程、外部渠道里的人工操作不在这些里程碑之内。

## 本轮验证

仅完成设计和布局草图，未实现扩展运行时或 LoopX 接入。草图使用示例数据，已在 Chromium 的桌面与手机尺寸、亮色与深色下查看，检查了切换看板/会话、展开详情和手机状态页签；没有横向溢出或页面脚本错误。未测实体手机。文档相对链接和空白检查通过。
