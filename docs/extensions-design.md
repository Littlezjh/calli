# 小核心与插件化

状态：方向已确定，以下都尚未实现：插件运行时、BotMux 接入、线程深链、统一事件语义。第一条待验证集成是「BotMux 外部提醒」，它的接法验证完成后，再决定 Limi 是否需要插件运行时及其范围。本文的「插件」与「扩展」指同一机制。

## 目标与边界

Limi 的核心负责连接 agent、管理会话、收发消息、展示进展和处理审批，不开插件时这条路径完整可用。鉴权、权限校验、事件存储及 agent 协议适配也在核心；agent 差异继续集中在 `packages/daemon/src/adapters/`，插件只消费统一事件和 capabilities。agent 自己的 skills、工具和扩展仍由它自己运行，Limi 的插件补充的是人的管理体验。

新增功能先问：关掉它，用户还能连接、发送任务、看进展和审批吗？能，就优先做成插件，例如通知渠道、外部工具集成、自定义展示、额外统计和自动化；会影响基础流程正确性或所有插件共同边界的，留在核心。已有功能在后续修改时逐项评估是否迁移，适合的就迁成内置插件，行为保持一致。

长期目标是让用户按需叠加丰富的插件，界面和后台都可以有入口。为此先用一条真实集成把边界走通，再按实际需求逐步开放接口，不一开始就搭一整套平台。

## 现状

以下是代码里已有的能力，插件设计以此为起点：

- daemon 把每个线程的统一事件写入事件日志，并广播给进程内的订阅者（`ThreadManager.subscribe`）。`/api/stream` 向浏览器推送其中的列表级事件，包括 `turn.started`、`turn.done`、`turn.error`、`approval.request`/`approval.resolved` 和 `input.request`/`input.resolved`。这个流没有全局游标，断线后只能重新读取线程列表。
- 定时任务（`scheduler.ts`）和协作（`coordination.ts`）各自把 `turn.done`/`turn.error` 映射成结果，两处写法相近，没有共用。
- 站内提示（`web/src/notices.ts`）：其他线程等待审批、等待回答、计划待确认或出错时，页面内提示；正常完成默认不弹，由未读标记和标题计数呈现。
- 已更改文件卡片（「已更改 N 个文件」、行数、逐文件 diff）是核心的一部分。
- 页面一次只连一台机器，没有能直接打开某个线程的链接。
- 访问凭据只有一个全权 token。
- 等待中的审批和问题只存在内存里，daemon 重启后，对应的轮次会被补记为中断。

## 统一事件语义（待实现前提）

提醒和以后的插件都需要一个统一的判断：哪一轮结束了、结果是什么、哪里在等人。这个判断现在不存在，要在 daemon 里实现成一个函数或一个小模块，定时任务和协作也改用它，并带测试。下表是首版需要覆盖的情况：

| 情况 | 现在的事件 | 首版外部提醒 |
| --- | --- | --- |
| 正常结束 | `turn.done`，`stopReason` 不是 `cancelled` | 可选，默认关闭 |
| 主动停止 | `turn.done`，`stopReason: 'cancelled'`；agent 还没启动就被停掉也是这样 | 不提醒 |
| 失败 | `turn.error`，带 `message`，可能带 `code`（如 `plan_exhausted`、`permission_refused`）。失败的轮次只有 `turn.error`，不会再有 `turn.done` | 提醒 |
| 等待审批 | `approval.request`（`approvalId`），处理后有 `approval.resolved` | 提醒 |
| 等待回答、计划待确认 | `input.request`（`inputId`，`kind` 为 `question` 或 `plan`），处理后有 `input.resolved` | 提醒 |
| 历史导入 | 导入 agent 原有会话时，整段历史一次写入，`turn.started`/`turn.done` 带 `imported: true`，并逐条广播 | 不提醒 |
| 终端同步 | agent 在终端里跑过的轮次被补进来，带 `fromTerminal: true`，一次可能有多轮，同样逐条广播 | 不提醒 |
| 控制轮 | 运行中发送 `/goal`、`/goal pause`、`/goal clear`，daemon 会另开一轮立即应答，与正在运行的轮次并行；事件里目前没有标记，只能从 `turn.started` 的文字判断 | 不提醒；统一语义需要补一个明确标记 |
| 重启中断 | daemon 启动时、任何订阅者注册之前，给仍在运行的轮次补 `turn.error`（`code: 'interrupted'`） | 首版收不到，也不补发；以后可以在启动后汇总一条 |
| 协作成员 | 成员线程是普通线程；成员一轮结束（非主动停止）后，协作模块把结果作为新的一轮，投递给主控或给它发消息的成员 | 成员的等待审批或回答照常提醒（它会卡住整个协作）；成员的结束和失败不单独提醒，由收到结果的那一轮体现 |
| 排队消息 | 一轮结束（含失败）后，daemon 立即开始下一条排队消息 | 每次失败都提醒；成功提醒开启时，只在队列清空、线程回到空闲后发一次 |
| 定时任务 | 定时任务发起的是普通轮次 | 按普通轮次处理 |
| 分叉 | 复制的历史事件不广播 | 不涉及 |

统一判断输出的是：机器、线程、轮次、线程标题、结果（成功、失败、停止）、失败码、等待类型和对应的 `approvalId`/`inputId`，以及来源标记（导入、终端同步、控制轮、协作成员）。具体字段在实现时确定。

## 第一条集成：BotMux 外部提醒

人不在浏览器前时，把需要处理的事情送到飞书。BotMux 是外部工具，负责飞书投递；Limi 只负责说清楚发生了什么，并给出回到线程的链接。

### 首版范围

- 只覆盖 hub 本机的线程。远程机器上的线程怎么提醒、链接怎么带上机器，放到后续单独设计。
- 默认提醒等待审批、等待回答或计划确认、失败；成功提醒可选，默认关闭。站内对正常完成保持安静，是因为页面上有未读标记和标题计数；外部提醒面向不在页面前的人，两者不冲突。
- 消息只含机器、线程标题、状态和回到线程的链接；不带回复内容、文件或命令输出。
- 同一个审批、问题或轮次只发一次；短时间内的多条合并成一条，窗口长度实现时再定。发送前审批或问题已被处理的，丢弃这条待发提醒。
- 链接依赖线程深链（待实现，见下文）和用户配置的工作台访问地址。链接不带 token，打开后正常鉴权。
- 不额外启动 agent，不注入 prompt，不改 agent 的配置和目录，也不让 BotMux 接管 agent 的会话；一条提醒不应触发 BotMux 的模型轮次。

### 可靠性

- 首版用内存队列，设超时，失败做有限次重试并写日志。
- daemon 重启时，还没发出去的提醒会丢失；首次启用、停用期间和重启前的事件都不补发。
- 不承诺可靠投递，也不保证不重复：网络超时后的重试可能造成重复，能否避免取决于投递接口是否幂等。
- 停用插件或投递失败都不影响任务执行；核心流程不等待投递完成。

### 配置

沿用 daemon 现有的配置方式（`.env` 环境变量，或数据目录下的 JSON 文件，类似 `agents.json`），具体键名和接口在实现时确定。第三方凭据只在后台使用，不回传浏览器。首版不做设置页、持久队列和插件市场。

### 两条接法：先验证，再定运行时

**A. Limi 推送。** hub 里的后台插件订阅统一事件，调用 BotMux 在本机提供的接口完成投递。

- 待验证：BotMux 有没有可以指定接收目标、又不触发模型处理的纯投递接口。已知 [通用 Webhook](https://deepcoldy.github.io/botmux/webhook.html) 会触发机器人处理事件；`botmux send` 从所在的 BotMux 会话推断目标话题。这两个都不能直接用。BotMux 的本机 Companion API 是否合适，接入前确认。
- 这条路需要 Limi 有一个最小的后台入口：启动时调用 `activate(api)` 并返回清理函数，宿主只提供统一事件订阅、该插件自己的配置和日志，处理异常时隔离。

**B. BotMux 订阅。** 在 BotMux 一侧写插件（BotMux 有自己的插件和后台 service 机制），由它订阅 Limi 的事件流并投递。

- 待验证的前提：Limi 提供只读的订阅凭据（现有 token 是全权的，不能交给外部工具）；断线重连后能补上错过的事件（现有 `/api/stream` 没有全局游标，至少要能按线程列表补差）；统一事件语义在流里可见。
- 这条路下，Limi 不需要后台插件运行时，飞书凭据也不进 Limi。

哪条对核心改动更少、凭据扩散更少，同时满足首版范围，就用哪条。结论写回本文后再动手实现。

## 线程深链（待实现前提）

页面目前只能按页面打开（如 `#todos`），选中哪个线程不在地址里。首版提醒需要一个能直接打开 hub 本机某个线程的地址，未登录时先正常鉴权，登录后打开这个线程。带上机器的链接，和多机器提醒一起设计。

## 插件运行时

- 运行时不是首版的必做项。只有 BotMux 选定「Limi 推送」，或以后出现需要在 Limi 进程内运行的插件时，才按本节实现；如果选定「BotMux 订阅」，首版不建运行时。
- 需要时，第一版是随源码构建的可信 TypeScript 模块，默认关闭，显式启用。入口调用 `activate(api)` 并返回清理函数；宿主只提供该入口需要的接口，停用时调用清理函数，并兜底回收订阅。
- 插件接口不暴露 Hub token、原始 Api、文件写接口或修改 prompt 的入口。启用、停用和重连都不改变 agent 的配置。
- 事件处理出错时只影响这个插件，不能打断 SSE、阻止审批或影响发送；核心流程不等待插件。
- 可信模块不是安全沙箱，捕获异常也挡不住死循环或进程崩溃。这些接口是维护边界，不承诺防住恶意代码；支持任意第三方代码之前，需要另一套隔离和资源约束设计。
- 公共接口在出现第二个实际插件或明确需求时再提炼。

## 界面插件（方向）

界面插件是确定的方向，例如自定义结果卡片、状态展示（比如让一只宠物跟着线程状态变化）、额外的面板。等第一个核心还没有的展示需求出现，再按它开对应的挂载点和只读接口，不预先搭注册体系。届时遵守这些约束：

- 插件只拿只读数据。提示和跳转由宿主绘制，插件不直接操作 DOM，也拿不到 Api。
- 使用 `styles.css` 顶部的颜色、圆角、阴影变量，以及 Dialog、Popover 和 icons；手机和桌面用同一份组件。
- 每个插件有独立的错误边界；插件出错时，原始内容照常显示。
- 已有的已更改文件卡片和站内提示属于核心；以后如果迁成内置插件，按逐项迁移处理，行为保持一致。

## 远期方向

- 多机器提醒：在哪台机器发出、链接怎么带上机器。可以由 hub 经已有隧道订阅各机，也可以各机自己配置 hub 地址和机器标识。
- 浏览器系统通知（`TODO.md` 第 5 节）和其他消息渠道。
- 界面插件；需要任务操作权限的自动化插件；第三方插件的加载、分发和市场。这些各自单独设计权限和隔离，不因为插件可扩展就默认开放。

不在当前设计范围：插件给 agent 注入或修改 prompt。这条和「不干扰 agent」的原则冲突，本设计的所有插件都不改 prompt；以后真有需求，要另行评估是否值得改变这条边界，不作为插件的远期能力。

## 实施顺序与验收

1. 验证 BotMux 的两条接法，把结论和选定方案写回本文。
2. 实现统一事件语义（测试覆盖上表每一行），定时任务和协作改用它；实现 hub 本机的线程深链。
3. 按选定的接法实现首版提醒。
4. 验收：
   - 浏览器关闭后仍能收到提醒。
   - 等待审批、等待回答、计划待确认、失败各提醒一次；发送前已处理的不再发。
   - 成功提醒默认关闭；开启后，排队的多条消息只在队列清空时提醒一次。
   - 主动停止、历史导入、终端同步、控制轮、分叉和重启中断都不提醒；协作成员的等待照常提醒，成员结束不单独提醒。
   - 超时和有限重试生效，失败有日志；停用后不再投递。
   - 发给 agent 的消息与不开插件时完全一致，没有新增 agent 请求，没有写入 agent 的配置或目录。
   - 凭据不出现在任何浏览器响应里。新接口有测试，判断只依据统一事件，不按 agent 名称分支。
   - 深链在桌面和手机、亮色和深色下完成浏览器验收。

官网只表达「默认简单，按需扩展」的方向，并标注扩展机制仍在规划中；具体首批内容以本文为准。
