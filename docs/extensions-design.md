## 两条接入路径

**agent 资源**指各家 agent 自己的 skills、MCP 配置、原生插件，以及记忆等生成状态和指令文件；**Limi 扩展**把外围工具接进 Limi 的界面。下文的「扩展」均指 Limi 扩展。

- **资源管理路径**：兼容的 skills 和 MCP 通过已有页面与适配器管理，安装资源不需要运行时 hook。生成状态和指令文件能做哪些操作分别设计，见「agent 资源管理」。
- **Limi 扩展路径**：外围工具提供状态、操作和提醒，优先通过清单接入，需要逻辑时使用独立进程，由宿主绘制界面。

agent 原生资源按各家的机制生效，Limi 扩展由扩展宿主管理，两者不能混为同一种插件。Limi 扩展不进入 agent 的循环，不给模型注册工具，不改上下文和 prompt。

工具接入后，状态关联到对应的机器和线程，也能从手机访问。已有独立界面的工具可以保留自己的界面，由 Limi 提供入口。

## 扩展越多，界面不能越乱

- **默认界面不变。** 不装扩展时和现在一样；装了也只出现在相关的地方，例如 LoopX 只出现在它推进的线程上。
- **一个入口。** Limi 扩展和各家 agent 的扩展都在「配置 → 扩展」一页管理：安装、启用、设置、查看它能做什么。
- **由 Limi 来画。** 扩展提供数据和声明，Limi 用自己的组件绘制：`styles.css` 顶部的颜色、圆角、阴影变量，Dialog、Popover 和 icons，手机和桌面同一份。第三方的东西看起来也像原生的。
- **同一位置由宿主聚合。** 多个扩展落在同一位置时，由 Limi 聚合或折叠，例如状态条始终只有一行，多个扩展的状态合在这一行里，点开再分别看；不堆多条常驻的状态条。扩展加的东西都带来源标记（图标和名称）。

## 边界

- **Limi 的扩展不进 agent 的循环。** 扩展运行时不给模型注册工具，不改上下文，不改系统 prompt，不改写用户消息。轮次之内的需求交给 agent 自己的 skills、hooks 和扩展。给 agent 注入或修改 prompt 不在本设计范围内。
- **审批由人处理。** 扩展不能替人允许或拒绝。
- **宿主不提供写 agent 目录和配置的接口。** `AGENTS.md` 要求不改 agent 的目录、配置和会话，扩展须遵守这条约束。技能页和 MCP 页是现有的、单独设计过的特定入口，它们的写入方式不会自动成为第三方扩展的通用写权限。让扩展通过 Limi 改 agent 配置是待确认的提案；以后若获批准，也必须走宿主和适配器的受控操作，执行前预览目标和改动，不给扩展任意写文件的接口。
- **给 agent 发消息是单独的任务控制权限。** 只对用户授权过的线程生效；发出的消息在线程里可见，并标明来自哪个扩展。这和偷偷改写用户消息或 prompt 是两回事。
- **核心流程不做成扩展。** 连接、鉴权、发送和审批留在核心；agent 差异继续只放在 `packages/daemon/src/adapters/`，扩展只读统一事件和 capabilities，不按 agent 名称分支。
- 宿主不向扩展提供 Hub token，也不提供原始 Api。扩展进程和 daemon 是同一个系统用户、没有沙箱，所以这是扩展须遵守的约束，不是隔离保证。

## 现状

以下是代码里已有的，设计以此为起点：

- daemon 把每个线程的统一事件写入事件日志，并广播给进程内的订阅者（`ThreadManager.subscribe`）。`/api/stream` 向浏览器推送其中的列表级事件，包括 `turn.started`、`turn.done`、`turn.error`、`approval.request`/`approval.resolved` 和 `input.request`/`input.resolved`。这个流没有全局游标，断线后只能重新读取线程列表。
- 定时任务（`scheduler.ts`）和协作（`coordination.ts`）各自把 `turn.done`/`turn.error` 映射成结果，两处写法相近，没有共用。
- 原生目标：`/goal` 经适配器接入（`capabilities.goal`、`controlGoal`），由 agent 自己续轮。
- 技能页和 MCP 页跨机器、跨 agent 管理 skills 和 MCP；目录和配置文件位置只在适配器里（`skillDirs()`、`mcpServers()` 等），见 `PLAN.md`。
- 站内提示（`web/src/notices.ts`）：其他线程等待审批、等待回答、计划待确认或出错时，页面内提示；正常完成默认不弹，由未读标记和标题计数呈现。
- 已更改文件卡片是核心的一部分。
- 页面一次只连一台机器，没有能直接打开某个线程的链接。
- 访问凭据只有一个全权 token。
- 等待中的审批和问题只存在内存里，daemon 重启后，对应的轮次会被补记为中断。

## 扩展怎么接入（待设计、待验证）

工具作者的接入成本要尽量低。分三层，越往下越少用：

1. **清单。** 一个 JSON 文件，声明怎么检测工具是否装好、哪条命令输出状态 JSON、有哪些操作、什么事件触发什么命令、需要哪些设置项。Limi 执行命令，再按声明绘制界面。有命令行、能输出 JSON 的工具，大多写一份清单就够。
2. **独立进程。** 需要自己逻辑的扩展（订阅事件后自行判断、决定下一轮）以独立进程运行，通过 stdio 上的 JSON-RPC 和 Limi 通信，用什么语言写都行。是否直接采用 MCP 及其界面扩展作为协议，待调研；能用的话，已有的 MCP 服务接入成本最低。
3. **界面组件。** 声明式组件画不出来的复杂视图，才允许在面板和独立页面里用 React 组件，带独立的错误边界。先只给内置扩展用。

扩展默认在 Limi 进程外运行：崩溃不拖垮 hub，也不限语言。统一调度入口、权限检查和界面绘制都在核心，不要求扩展和 daemon 同进程。扩展宿主按首批集成的实际需要分步建，不先建完整平台。

清单示意（格式是设计稿；LoopX 的命令和参数是假设，接入前核实）：

```jsonc
{
  "id": "loopx",
  "name": "LoopX",
  "description": "长程目标、待办和额度",
  "requires": { "command": "loopx" },
  "scope": "thread",
  "permissions": ["run-commands", "read-thread-events"],
  "status": { "command": ["loopx", "status", "--json"], "refresh": "turn-finished", "show": "status-bar" },
  "panel": { "title": "LoopX", "command": ["loopx", "status", "--json"], "show": "sections" },
  "attention": { "path": "decisions", "label": "等你决定" },
  "actions": [{ "id": "pause", "label": "暂停", "command": ["loopx", "pause"], "confirm": true }]
}
```

### 执行命令的约束

- **两种执行要分开。** 一种是 Limi 为扩展执行清单里的命令，另一种是 agent 在轮次里自己运行同一个工具。本节只管前一种。
- **命令固定。** 可执行文件和参数模板写在清单里；参数只能来自声明过的字段，不拼接 shell 字符串。
- **目录受限。** 线程范围的命令在线程目录里执行，机器范围的在扩展自己的目录里执行，都受工作目录白名单约束。
- **有超时、能取消，输出有大小上限。** 超时、取消和失败都在界面上如实显示。
- **声明副作用，按触发方式执行。** 每条命令声明自己是只读还是有副作用；实际有没有副作用，接入时核实。
  - 只读命令可以自动执行，例如刷新状态。
  - 用户点击的操作：有副作用的，需要时先确认。
  - 事先授权的自动动作：例如事件发生时触发提醒，或授权后的续轮。只在授权的范围内执行，范围包括哪些事件、哪些命令、哪些线程。
  - 写 agent 配置不会因为授权了提醒或续轮而自动获得。
- **这些是宿主的调用约束，不是隔离。** 参数和目录校验约束的是 Limi 怎么调用命令；被调用的程序和扩展进程以 daemon 用户的身份运行，和终端功能同级。安装即信任：安装时列出扩展要执行的命令和权限，用户确认后才启用。

## 界面：宿主组件和固定位置

扩展的内容用宿主组件绘制：状态文字和色调、进度、标记、清单、表格、键值对、Markdown、操作按钮、表单字段。下表是候选位置，不是承诺都会开放：

| 候选位置 | 桌面 | 手机 | 典型用途 |
| --- | --- | --- | --- |
| 线程状态条 | 输入框上方一行 | 同一位置，点开展开 | 长程进度、额度 |
| 线程标记 | 侧栏线程行右侧，加待处理原因 | 同 | 被谁推进、等你决定 |
| 线程菜单和 `/` 面板 | ⋯ 菜单、命令面板 | 同 | 启用、操作 |
| 来源标签 | 由扩展发起的那一轮，标明来源 | 同 | 透明 |
| 结果卡片 | 工具结果下方 | 同 | 测试报告、截图 |
| 侧边面板 | 右侧面板多一个标签 | 全屏页 | 详细状态、待办 |
| 工作视图 | 主区域页面，入口可固定在侧栏；未固定的收在「更多」 | 主区域全屏 | 看板、跨线程总览 |
| 设置 | 「配置 → 扩展」 | 同 | 安装、启用、设置项、权限 |

首批只开放首批集成实际用到的位置，其余等真实需求出现再开。多个扩展同一位置时由宿主聚合或折叠，见上文。

「配置 → 扩展」负责安装和启停，不承载日常工作的看板。首个看板最初沿用 [看板设计](board-tags-design.md) 的线程视角，现已改为计划项视角（见 [工作台扩展](extension-workbench-design.md) 开头），列仍不能拖动。业务任务的完成由计划项或外部数据源确认，不从 `turn.done` 推断。会话里只保留一行聚合摘要；卡片默认最多一行扩展摘要，其余按需展开。

## 权限（设计稿）

| 权限 | 能做什么 | 条件 |
| --- | --- | --- |
| 事件和摘要 | 读统一事件和线程摘要，只含白名单里的元数据，不含对话内容（见「数据范围」） | 安装时确认 |
| 读进度 | 读已授权线程中 agent 报告的步骤快照，包含步骤文字；不等于读取整段对话 | 单独授权，按线程生效 |
| 读工作数据源 | 读指定来源的目标、工作项与完成依据；目标和任务文字属于内容 | 按来源与关联线程授权，不因启用看板而自动获得 |
| 读线程文件 | 只读，只限扩展关联的线程（例如被它推进的线程）的目录，经过文件查看器同一套边界检查；不是所有线程 | 安装时确认，按线程生效 |
| 执行命令 | 执行清单里声明的命令，约束见上文 | 安装时确认；自动执行的部分按授权范围 |
| 提醒 | 通过宿主的提醒接口发出；投递渠道本身也是扩展 | 安装时确认 |
| 读对话 | 读关联线程某一轮的用户消息和回复，不含思考内容 | 安装时单独确认，按线程生效 |
| 读工具结果 | 读关联线程里工具的结果和命令输出，例如给结果卡片用 | 安装时单独确认，按线程生效 |
| 任务控制 | 给用户授权过的已有线程发可见消息 | 用户按线程授权 |

不在表里的：

- **写 agent 的目录和配置**：待确认的提案，见「边界」。
- **新建线程**：扩展能在哪些目录、用哪个 agent 实例、由谁授权新建线程，另行设计；不能理解为对还不存在的线程预先授权。

这张表描述的是宿主允许扩展调用什么，不承诺隔离：扩展进程和它执行的命令都以 daemon 用户的身份运行。

## 接口与生命周期（设计稿）

这一节先把接口留好：扩展在哪些时刻收到通知、宿主什么时候向扩展要内容、扩展能调用哪些宿主接口。之后的集成按生命周期逐个接上。下面的名称都是草案，具体字段、方法名和传输细节在实现时确定。

### 三种 hook，不做拦截

| 形态 | 方向 | 时机 | 对核心的影响 |
| --- | --- | --- | --- |
| 通知 | 宿主 → 扩展 | 事情发生之后 | 无。异步投递，核心不等待 |
| 请求 | 宿主向扩展要结果 | 宿主需要时，分三类，见下 | 只影响扩展负责的那部分；核心的发送和审批不等待任何请求 |
| 动作 | 扩展 → 宿主 | 扩展主动调用 | 受权限和授权范围约束 |

不提供「事前拦截或改写」的 hook：扩展不能否决或修改发送、审批、建线程，也不能改写消息或 prompt。旧设计里 `turn.beforePrompt` 这类 hook 不再保留。

扩展只收到清单里声明订阅的 hook；数据只来自统一事件和 capabilities，不按 agent 名称分支；清单声明 `apiVersion`，同一主版本内只增不改。

### 数据范围：按权限投影，不转发原始事件

现有事件和线程视图里混着对话内容：`turn.started` 带消息文字和图片，`approval.request` 带工具调用的输入（`toolCall`），`input.resolved` 带用户的回答，线程视图带 `preview` 和排队消息的文字（`queued[].text`）。宿主不把这些原样转给扩展，而是按权限投影：

- **事件和摘要**：通知、`threads.list`/`threads.get`、`turns.summary` 默认只返回白名单里的元数据，例如机器、线程 id 和标题、状态、agent 实例、轮次 id、结果、失败码、等待类型和 id、时间、改动文件的路径和行数。不含消息文字、图片、工具的输入和输出、问题的答案、`preview`、排队消息的文字。线程标题可能取自第一条消息的首行，这一点在安装确认时说明。
- **读对话**（`turns.transcript`）：只限扩展关联的线程，单独授权；只给用户消息和回复，不开放思考内容。
- **读进度与工作数据源**：计划步骤、目标和任务文字属于内容，不能通过默认元数据订阅泄露。看板读到的范围不得超过用户授权给它的来源和线程；来源身份由宿主标注。
- **读工具结果**：`card.forToolResult` 的输入是工具结果和命令输出，属于内容，需要单独的读取范围；不能因为它是「画界面」的请求就绕过权限。
- 请求的输入同样受这些约束：宿主发给扩展的请求只带该扩展有权看到的字段。

### 请求的契约

请求分三类，超时后的处理各不相同：

| 类别 | 例子 | 超时或出错时 |
| --- | --- | --- |
| 只读查询 | `extension.detect`、`capability.status`、`ui.*`、`progress.snapshot`、工作数据源快照、`card.forToolResult`、`handover.context` | 降级：对应位置不显示，或显示「暂时无法获取」，下次刷新再试 |
| 续轮决策 | `driver.next` | 暂停该扩展对这个线程的推进，并显示原因；不当作空结果，也不自动继续 |
| 副作用投递 | `channel.deliver` | 结果未知。有限次重试，重试沿用同一个稳定的投递 id，接收方可据此去重；仍可能重复，界面和文档都这样说明 |

每个请求带请求 id、截止时间、取消信号和结果大小上限。宿主丢弃这些迟到的响应：超过截止时间、请求已取消、扩展已停用或被撤权、线程或推进权的版本已经变化。对丢弃的响应，宿主不再采纳其结果，也不据此发起后续动作，特别是不能再发出一轮；但已经发生的命令或外部投递的副作用，不会因为超时、取消或丢弃响应而撤回。扩展停用时，宿主取消尚未执行的重试；已经在途的投递不保证撤销。

### 给 agent 发消息：只有两条路

- **自动推进只能经 `driver.next`。** 每次都经过同一组检查：持有推进权、和原生循环互斥、排在用户消息和协作投递之后、入队前重新核对版本、不超过自动轮数上限。`threads.send` 不能用来绕开这些检查另起一个循环。
- **`threads.send` 只用于用户点击触发的一次发送**，例如面板里的「让 agent 继续」按钮。这次动作由宿主的交互上下文绑定扩展、线程和参数，只能使用一次；宿主不接受扩展自己声明「这是用户点击的」。发送前同样复核这个扩展对该线程仍有任务控制授权。
- 两条路发出的消息，来源都由宿主标注为该扩展（点击触发的再注明是用户点的）；扩展不能把自己的消息标成用户发的。

### 投递与恢复

- 同一线程内，通知按事件发生的顺序投递。尽力投递，不落盘。
- 每条通知带事件标识（线程内的序号）和宿主代次（每次 daemon 启动不同），扩展据此发现重启。
- 每个扩展的待投递队列有上限；溢出时丢弃，并发一条「需要重取当前状态」的通知。
- `threads.list` 只能重取当前状态。停用、重启或溢出期间出现又消失的失败和等待，用它补不回来，所以不能称为「已恢复全部事件」。
- BotMux 首版仍然不补发历史。外部订阅方案如果需要恢复历史，是另一项待设计的能力。

### 扩展的启停

- **检测和启动失败要看得见。** 依赖检测不通过，在「配置 → 扩展」里显示缺什么，不启动；启动失败显示原因和日志摘要；反复崩溃时，在有限次重启之后停下，显示「已停止」和原因。
- **停用、撤权或崩溃时由宿主兜底清理。** 注销它的订阅和界面内容，取消所有挂起的请求，释放推进权（相关线程的推进暂停，并显示原因）；之后到达的旧响应一律无效，不能再发出任务。`extension.deactivating` 只是让扩展尽力自己清理。
- **中途启用不依赖 `machine.ready`。** `machine.ready` 只在 daemon 启动时发一次；任何时候启用的扩展，都通过 `extension.activated`（带宿主代次）开始，再用 `threads.list` 等接口读当前快照。
- `ui.invalidate` 和 `storage` 只作用于该扩展自己的命名空间。

字段名和传输细节可以以后定，但上面这些行为是契约的一部分。

### 事件字段

- **轮次的来源分三个维度，不合成一个枚举。** 发起者：用户、定时任务、协作投递、交接、扩展等；派发方式：直接开始，或排队后开始（用户消息也会排队）；性质：导入、终端同步、控制轮。具体结构待定。现在 `turn.started` 已有 `coordination`、`handover`、`scheduled`、`fromTerminal`、`imported`；排队派发和控制轮没有标记。
- **`turn.finished` 的摘要可能缺失或不完整。** 不是每家 agent 都报告改动和用量；缺的字段就不给，不填 0；模型估算的数字要标明是估算，不当作事实。
- **和现有事件兼容。** 现有的 `thread.created` 补上来源，并在分叉时补发；新增 `thread.changed`，带改动字段；现有的 `thread.updated` 保留，浏览器继续使用。

### 三种接入方式怎么对应

- **清单**：通知触发声明的命令，事件里的白名单字段只能作为声明过的参数传入。只读查询执行声明的只读命令，读取它输出的 JSON；`channel.deliver` 执行声明为有副作用的命令，属于事先授权的自动动作，按授权范围执行；首批不支持用清单实现 `driver.next`。动作只有 `notify` 和执行声明的命令。
- **独立进程**：用 JSON-RPC 收通知、响应请求、调用宿主接口，名字和上表一一对应（传输细节待定）。
- **内置扩展**：同一套 hook，在 daemon 进程内直接调用。

### 记忆看板（内置可选扩展）

`packages/ext-memory` 是独立视图包，只依赖公开的扩展契约。默认未安装；在「配置 → 扩展」安装并确认 `memory.read` 后，侧栏才出现「记忆」。停用或卸载后隐藏入口、结束页面刷新订阅，后端拒绝新查询及尚未返回的旧查询。安装只记录 Limi 的扩展状态，不修改 agent 的目录、配置或会话。

数据链路：Codex 已有文档 → `adapters/codex-memory.ts` → 扩展宿主的 `memory.sources/list/read` → `WebHost.memory` → 看板。适配器按实例环境解析 Codex Home；只有声明 `capabilities.memory` 且实现读取接口的实例成为来源。以真实目录合并共用存储的实例，前端不按 agent 名称分支。权限范围是当前机器上受支持实例的记忆文档，安装弹窗说明其可能跨项目；不沿用线程文件权限来放宽文件查看器的范围。

首版识别 `memory_summary.md`、`MEMORY.md`、`raw_memories.md` 和 `rollout_summaries/`、`raw_memories/`、`skills/` 中的 Markdown。目录和文件名知识只在 Codex 适配器中。拒绝相对越界、子路径符号链接、非普通文件和二进制内容；列表最多 500 份文档、2000 个目录项，读取最多 512 KiB，界面说明扫描不完整或内容截断。记忆正文不写入 Hub 数据库或浏览器存储。

页面支持来源切换、文档分类、标题与摘要搜索、Markdown 预览和原文。标题和摘要来自文档前 4 KiB，并非全文搜索；日期表示文件修改时间，并不声称是记忆生成时间。预览不执行 HTML，不加载外部媒体，不激活文档链接。桌面列表与详情并排，手机逐页阅读。读取不到时区分没有目录、空目录、不可读和无法识别的格式。

`WebHost.memory.subscribe` 提供刷新提示：页面可见时每 30 秒、重新可见和连接恢复时重新查询，也可手动刷新。离开页面即取消订阅。没有把 `turn.finished` 当作记忆生成通知，也没有安装 Codex 内部 Hook；Codex 在 Hub 外生成的记忆同样会被后续查询发现。示例模式没有原生记忆来源，展示空状态。

本版不接入编辑、删除、记忆生成开关、上下文注入、数据库分析或外部扩展包下载。实际安装的 Codex 版本与文件布局需在目标实例上验证。

### 例子：记忆（设计说明）

记忆是「各家 agent 能力不一样」的典型例子，用来说明上面的接口怎么分工。原生只读看板已经按上述首版范围实现；其他记忆管理与共享服务仍是设计说明。

**四件事分开看，按实例探测。**

- agent 有这个能力：这个版本的 agent 支持记忆。
- 已启用：这个实例的配置里打开了。
- Limi 能管理：Limi 的适配器接好了查看、编辑或删除的接口。agent 有记忆功能，不代表这些接口已经接好。
- 实际可用：在这个实例上真实调用验证过。

界面显示的状态是：未配置、已配置待验证、可用、不可用，并写明原因和来源。探测结果只代表那一个实例，不推到同类型的其他实例；通用规则里不写死某个功能的成熟度或存储文件名。先用 `capability.status` 报告状态，不预先建完整的 provider 框架。

**几种实现可以任选，也可以并存。** 记忆可以来自 agent 原生的功能、用户选择安装的 agent 原生扩展，或几个 agent 共同接入的共享服务（例如一个记忆 MCP 服务）。这不是必须依次补齐的步骤，原生和共享也可以同时存在。缺失的如实显示；只对兼容的扩展给出安装选项。

**装了同一个包，不等于共享数据。** 要共享，几个 agent 必须指向同一个逻辑存储或命名空间，并验证读写授权和并发；跨机器还需要服务能被访问到。以 MCP 官方的 [memory 示例](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/README.md) 为例：它的数据存在 `MEMORY_FILE_PATH` 指定的本地文件里，多个进程共享同一个文件需要文件锁。它不是跨机器服务，在 Limi 里也还没有跑通过。

**交接不等于继承记忆。** 交接后，Codex 的本地记忆不会自动被 pi 继承，记忆仍在 Codex 那边，并没有丢失。交接内容里明确写出的任务信息，和记忆继承是两回事。`handover.context` 只能提供一段可见、可编辑的内容，由用户决定是否发送。

**说明文件不是记忆服务。** `AGENTS.md`、`CLAUDE.md` 是说明文件，不是 MCP。各家 agent 加载哪些说明文件需要逐家核实；现有的 MCP 页不安装说明文件。

**两层边界。**

- Limi 不自己生成记忆，也不把记忆注入 agent 的上下文。
- 用户选择安装的 agent 原生扩展，在 agent 内部运行，可以管理它自己的记忆上下文；这是 agent 自己的行为。

这不放宽配置写入的原则：和记忆有关的 agent 配置，仍然只能经单独设计的特定入口写入。

### 核心需要先补的

按用到它的集成分三组。BotMux 首版只依赖第一组，不必等扩展宿主和调度入口落地。

**BotMux 首版**

- 统一事件语义：`turn.finished`、`attention.*`，以及区分导入、终端同步、控制轮的性质标记（控制轮现在没有标记）。
- hub 本机的线程深链。
- 接法 A 需要一个运行提醒的最小入口；接法 B 需要只读的订阅凭据。二选一，见 BotMux 一节。

**扩展宿主和界面**

- 扩展进程的管理：启动、停止、超时、崩溃后有上限的重启，以及上文的启停契约。
- 按权限投影的数据视图，以及请求的契约（请求 id、截止时间、取消、大小上限、丢弃迟到响应）。
- 有界的待投递队列，以及「需要重取当前状态」的通知。
- 现有的 `thread.created` 补上来源，并在分叉时补发；新增 `thread.changed`，带改了哪些字段；保留 `thread.updated`。
- agent 实例变化的通知，以及能力矩阵。

**自动推进**

- 统一调度入口和推进权，`driver.next` 依赖它们。
- 轮次来源里的「扩展」发起者和「排队后开始」派发方式。
- 自动轮数上限，以及和原生循环的互斥检查。

## 统一事件语义（待实现前提）

提醒和以后的扩展都需要一个统一的判断：哪一轮结束了、结果是什么、哪里在等人。这个判断现在不存在，要在 daemon 里实现成一个函数或一个小模块，定时任务和协作也改用它，并带测试。下表是首版需要覆盖的情况：

| 情况 | 现在的事件 | 首版外部提醒 |
| --- | --- | --- |
| 正常结束 | `turn.done`，`stopReason` 不是 `cancelled` | 可选，默认关闭 |
| 主动停止 | `turn.done`，`stopReason: 'cancelled'`；agent 还没启动就被停掉也是这样 | 不提醒 |
| 失败 | `turn.error`，带 `message`，可能带 `code`（如 `plan_exhausted`、`permission_refused`）。失败的轮次只有 `turn.error`，不会再有 `turn.done` | 提醒 |
| 等待审批 | `approval.request`（`approvalId`），处理后有 `approval.resolved` | 提醒 |
| 等待回答、计划待确认 | `input.request`（`inputId`，`kind` 为 `question` 或 `plan`），处理后有 `input.resolved` | 提醒 |
| 历史导入 | 导入 agent 原有会话时，整段历史一次写入，`turn.started`/`turn.done` 带 `imported: true`，并逐条广播 | 不提醒 |
| 终端同步 | agent 在终端里跑过的轮次被补进来，带 `fromTerminal: true`，一次可能有多轮，同样逐条广播 | 不提醒 |
| 控制轮 | 运行中发送 `/goal`、`/goal pause`、`/goal clear`，daemon 会另开一轮立即应答，与正在运行的轮次并行；事件里目前没有标记，只能从 `turn.started` 的文字判断 | 不提醒；统一语义需要补一个明确标记 |
| 重启中断 | daemon 启动时、任何订阅者注册之前，给仍在运行的轮次补 `turn.error`（`code: 'interrupted'`） | 首版收不到，也不补发；以后可以在启动后汇总一条 |
| 协作成员 | 成员线程是普通线程；成员一轮结束（非主动停止）后，协作模块把结果作为新的一轮，投递给主控或给它发消息的成员 | 成员的等待审批或回答照常提醒（它会卡住整个协作）；成员的结束和失败不单独提醒，由收到结果的那一轮体现 |
| 排队消息 | 一轮结束（含失败）后，daemon 立即开始下一条排队消息 | 每次失败都提醒；成功提醒开启时，只在队列清空、线程回到空闲后发一次 |
| 定时任务 | 定时任务发起的是普通轮次 | 按普通轮次处理 |
| 分叉 | 复制的历史事件不广播 | 不涉及 |

统一判断输出的是：机器、线程、轮次、线程标题、结果（成功、失败、停止）、失败码、等待类型和对应的 `approvalId`/`inputId`，以及来源标记（导入、终端同步、控制轮、协作成员）。具体字段在实现时确定。

## 线程深链（待实现前提）

页面目前只能按页面打开（如 `#todos`），选中哪个线程不在地址里。提醒需要一个能直接打开 hub 本机某个线程的地址，未登录时先正常鉴权，登录后打开这个线程。带上机器的链接，和多机器提醒一起设计。

## 首批真实集成

线程执行看板是首个验证界面宿主的集成，详见 [工作台扩展](extension-workbench-design.md)。以下工具按需要验证其他能力，编号不是实施先后；BotMux 可以并行验证通知出口。

用三个真实集成定下清单、协议和界面组件，接口从它们里提炼，不凭想象设计。

### 1. BotMux 外部提醒

人不在浏览器前时，把需要处理的事情送到飞书。BotMux 负责飞书投递；Limi 只负责说清楚发生了什么，并给出回到线程的链接。

**首版范围**

- 只覆盖 hub 本机的线程。远程机器上的线程怎么提醒、链接怎么带上机器，放到后续单独设计。
- 默认提醒等待审批、等待回答或计划确认、失败；成功提醒可选，默认关闭。站内对正常完成保持安静，是因为页面上有未读标记和标题计数；外部提醒面向不在页面前的人，两者不冲突。
- 消息只含机器、线程标题、状态和回到线程的链接；不带回复内容、文件或命令输出。
- 同一个审批、问题或轮次只创建一个投递任务，重试可能造成重复；短时间内的多条合并成一条，窗口长度实现时再定。发送前审批或问题已被处理的，丢弃这条待发提醒。
- 链接依赖线程深链和用户配置的工作台访问地址。链接不带 token，打开后正常鉴权。
- 不额外启动 agent，不注入 prompt，不改 agent 的配置和目录，也不让 BotMux 接管 agent 的会话；一条提醒不应触发 BotMux 的模型轮次。

**可靠性**

- 首版用内存队列，设超时，失败做有限次重试并写日志。
- daemon 重启时，还没发出去的提醒会丢失；首次启用、停用期间和重启前的事件都不补发。
- 不承诺可靠投递，也不保证不重复：网络超时后的重试可能造成重复，能否避免取决于投递接口是否幂等。
- 停用或投递失败都不影响任务执行；核心流程不等待投递完成。

**配置**：首版沿用 daemon 现有的配置方式（`.env` 环境变量，或数据目录下的 JSON 文件，类似 `agents.json`），具体键名实现时确定；扩展设置页做好后迁过去。第三方凭据只在后台使用，不回传浏览器。

**两条接法，先验证再选**

- **A. Limi 推送。** Limi 侧的扩展（清单里的触发命令，或独立进程）在事件发生时调用 BotMux 的纯投递接口。待验证：BotMux 有没有能指定接收目标、又不触发模型处理的接口。已知 [通用 Webhook](https://deepcoldy.github.io/botmux/webhook.html) 会触发机器人处理事件，`botmux send` 从所在的 BotMux 会话推断目标话题，都不能直接用；本机 Companion API 是否合适，接入前确认。
- **B. BotMux 订阅。** 在 BotMux 一侧写插件（BotMux 有自己的插件和后台 service 机制），订阅 Limi 的事件流并投递。待验证的前提：Limi 提供只读的订阅凭据（现有 token 是全权的，不能交给外部工具）；统一事件语义在流里可见。首版断线后的处理：重新订阅后读取当前快照，核对仍待处理的审批和问题；断线期间已经结束的失败或等待不回放。以后如果要求完整的历史恢复，需要另行设计游标和回放能力。这条路下，飞书凭据不进 Limi。

哪条对核心改动更少、凭据扩散更少，同时满足首版范围，就用哪条。结论写回本文后再实现。

### 2. LoopX 长程推进（待验证）

[LoopX](https://github.com/loopx-project/loopx) 自己不跑模型（它的说法是 "Your harness runs the turn. LoopX carries the work"）：状态放在 `.loopx/`，agent 在轮次里通过 LoopX 的 skills 调用它的命令。它有自己的浏览器和 PWA 看板（`loopx dashboard`），并且按 README 的描述，已经接到各家 agent 的原生循环上：Codex CLI 用可见的 `/goal`、Codex App 用心跳自动化，Claude Code 用 `/loopx` 再接原生 `/loop`，pi 用可选的 goal 扩展。接进 Limi 按这个顺序：

1. **验证原生接法在 Limi 里能不能用。** agent 经 Limi 运行时，LoopX 依赖的原生循环（Codex `/goal`、Claude `/loop`、pi 的 goal 扩展）是否照常工作，逐家核实。Limi 已经通过适配器接入了原生 `/goal`。
2. **先只读展示，再逐项接操作。** 以工作数据源接入宿主投影，会话摘要、看板和详情显示同一份目标、工作项和待处理状态；完整功能可以链接到 LoopX 自己的界面。固定版本源码已确认 `loopx status --format json --goal-id <id>` 的格式入口，尚未在 Limi 中实测；字段完整性、查询副作用、目标与线程关联及远程界面可达性仍需验证，证据见 [工作台扩展](extension-workbench-design.md)。暂停、回答待决定事项等操作核实真实语义后单独设计，不从只读展示推导控制权限。
3. **只有原生接法不够时，才考虑 Hub 驱动的续轮。** 有了可见的状态，并不意味着必须由 Limi 新建一套循环。如果确有需要，它是可选的推进扩展，需要任务控制权限和宿主的统一调度入口，接口待验证：
   - 一个线程同一时间只有一个推进者。和原生循环互斥；不能可靠知道原生循环当前状态时，不启动第二套循环。
   - 扩展异步给出「下一轮发什么」之后、真正排入队列之前，宿主重新检查：推进权和版本、线程是否暂停或删除、有没有待处理的审批、用户和协作的队列里有没有消息。等待期间用户对这个线程的任何操作，都让旧结果作废。
   - 只对用户授权过的线程生效；续轮消息在线程里可见并标明来自 LoopX；审批仍由人处理；宿主设自动轮数上限，daemon 重启后暂停。

agent 侧需要的 LoopX skills，由用户自己安装（在技能页或用 LoopX 自己的安装命令），扩展不替用户装。

### 3. 现有页面迁移（看板通过后再评估）

先只取现有技能页的只读部分（技能列表和各机器的状态），用宿主组件重新实现，和原界面并排对比。达到原界面的水准之后，再评估要不要迁完整页面（安装、同步、删除），不为了验证接口先重做整页。画不出原有水准，就先补宿主组件，而不是放宽到让扩展自带样式。

## agent 资源管理（待调研）

技能页和 MCP 页已经覆盖 skills 和 MCP。接下来调研各家 agent 的扩展形式：Claude Code 的插件、市场和 hooks，Codex 的扩展方式，pi 的 packages 和 extensions，以及哪些能跨 agent 统一查看。

- 资源分三类，不一律套用安装和移除：可安装的资源（包、skills、MCP 配置）；agent 生成的状态（例如记忆）；指令文件（例如 `AGENTS.md`、`CLAUDE.md`）。每一类能做哪些操作，分别设计。
- 统一管理不等于格式互通：只向兼容的实例安装；界面显示实际的机器和实例、各自支持什么，以及每个目标的操作结果。
- 沿用现有做法：位置和格式的知识只放在适配器里，前端按 capabilities 判断。
- 新增的写入入口（比如安装 Claude Code 插件）和技能页、MCP 页一样，作为核心里单独设计的特定入口，各自评审；现有资源页不自动批准新的写入入口，也不经由扩展的通用写权限实现。

## 远期方向

- 「配置 → 扩展」里的发现页和社区分发；清单和协议的版本兼容。
- 多机器提醒：在哪台机器发出、链接怎么带上机器。
- 浏览器系统通知（`TODO.md` 第 5 节）和其他消息渠道。
- Hub 驱动的目标续轮：作为可选的推进扩展，遵守上面的互斥和重新检查规则，不替代原生 `/goal`。

以下是盘点中发现的候选缺口，只是候选，未获授权实现：

- **外部渠道里的人工操作。** 例如在飞书里回复。普通回复、回答待处理的问题、审批权限是三种不同的授权，各需要身份绑定、操作权限、与机器、线程和请求 id 的绑定、过期和重复处理，以及处理记录；普通群消息或扩展上报不能当作用户批准。这和扩展自动替人审批不同，后者始终不提供。BotMux 首版仍然只有外发提醒和回到 Limi 的链接。
- **实例预设。** 即使写的是 Limi 自己的实例表，也会改变 agent 的命令、环境变量、模型网关和数据去向；要作为用户可见的受控实例操作单独设计，展示目标和改动。
- **新建线程。** 要定义创建范围：目标机器、实例、目录、权限模式、预算；先和现有的协作、定时任务对照，再定最小接口；不能借已有线程的任务控制权限无限派生。
- **执行环境**（worktree、容器等）留到远期，不扩展成编辑器或 agent 内部的工具运行时。

## 实施顺序与验收

1. 补首版线程执行看板需要的统一状态判断、按权限投影的线程快照与订阅、线程深链；将通用视图注册和路由接进宿主，替代逐个扩展硬编码页面的做法。
2. 看板作为本仓库独立包实现，只依赖公开契约；宿主提供三列看板和手机列表原语、启停与入口。未启用时不出现，暂不以标签或完整插件平台为前提。
3. 按权限加入步骤快照、关联计划项和最小工作投影。先接 Limi 计划来源，再接只读 LoopX 来源，让看板、会话摘要和详情读同一份状态；LoopX 的真实版本、字段、查询副作用和关联方式要验证。
4. BotMux 在统一事件语义和深链具备后并行验证两条接法，实现原定首版提醒。它不阻塞看板的界面契约验证。
5. 在看板与 LoopX 两个样例上确定清单与独立进程协议，再支持本地包和固定版本构建产物的安装、兼容检查、启停、升级与回退；仓库负责承载源码，不以任意仓库脚本作为安装入口。各家 agent 资源与 MCP 界面扩展的调研按接入需要进行。
6. 根据真实需求增加操作和原语，再评估现有页面迁移。Hub 驱动续轮仍须与原生循环互斥、按线程授权；不因接入看板而默认启动。
7. 有多个独立扩展之后再做发现页、社区分发与多机器聚合。细化里程碑和验收见 [工作台扩展](extension-workbench-design.md)。

通用验收：

- 不装扩展时，界面和行为与现在一致；装了只出现在相关的位置，多个扩展同一位置时由宿主聚合，带来源标记。
- 扩展崩溃、命令超时或失败，不影响连接、发送和审批，界面如实显示失败。
- 自动执行的命令不超出授权范围；用户点击的有副作用操作按声明确认。
- 发给 agent 的消息与不装扩展时一致，除非用户对该线程授权了任务控制，且续轮消息可见。
- 宿主不提供写 agent 目录或配置的接口；读线程文件只限扩展关联的线程；凭据不出现在任何浏览器响应里。
- 新接口有测试，判断只依据统一事件和 capabilities，不按 agent 名称分支。
- 桌面和手机、亮色和深色都在真实浏览器里看过。

接口契约的验收要能说明这四件事：

- 只订阅了事件和摘要的扩展，收到的 `turn.started`、`approval.request`、`input.resolved` 和线程摘要里，没有消息文字、工具输入或答案。
- 扩展停用或被撤权之后，才返回的 `driver.next` 响应被丢弃，不会发出新的一轮。
- 一次投递连续两次超时并重试，系统只说明「可能重复」，不承诺只发了一次。
- 待投递队列溢出或 daemon 重启后，扩展收到的是「需要重取当前状态」或新的宿主代次，系统不会宣称已经恢复了全部历史事件。

BotMux 首版另需验收：浏览器关闭后仍能收到提醒；等待审批、等待回答、计划待确认、失败各只触发一次投递（投递重试可能造成重复，见请求的契约），发送前已处理的不再发；成功提醒默认关闭，开启后排队的多条只在队列清空时提醒一次；主动停止、历史导入、终端同步、控制轮、分叉和重启中断都不提醒，协作成员的等待照常提醒；超时和有限重试生效，失败有日志，停用后不再投递。

官网表达的方向：一个简单的界面，把 agent 和它周边的工具串起来；扩展机制标注规划中，具体首批内容以本文为准。
