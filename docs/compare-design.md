# 同题对比设计

状态：设计稿，未实现。更新：2026-10-13。

## 核心决定

同一个任务、同一个起点，交给两个实例各做一份；用户看两份结果，选一份，留一句理由。这些成对的选择累积起来，就是用户自己的评测。

- **用户来判。** hub 不打分，不自动合并，不替用户选。
- **只比可比的东西。** 两份的起点必须逐字节相同；比的是相对这个起点的完整改动，不是聊天里零散的改动卡片。
- **不做日常跑分。** 普通线程的日志不进这里。不同 agent 平时接的任务难度不同，被停止也不等于不满意，从中算出的比例会误导。
- **不新增 agent 差异。** 全部用现有的线程、工作树和事件；适配器不用改，前端不按 agent 名字分支。

第一版只做两份，只支持新线程，目录必须是 git 仓库。

## 用户入口

1. 新线程的输入框上方，agent 选择器旁多一个「再找一个试试」。点了之后选第二个实例；两个实例各自保留自己的模型和思考强度。目录不是 git 仓库时这个入口不可用，并说明原因。
2. 写好任务，发送。hub 建两个工作树、两个线程，把同一段话（含图片）发给两边。
3. 侧边栏里两个线程合成一行「对比：标题」，带两个实例的标志和各自的状态点，和交接链的归组同一套做法。展开可以分别进入。
4. 两边都停下后，这一行出现未读标记。点开是对比页。运行中也能打开，没结束的一边显示「还在做」。
5. 在对比页选「用这份」「都保留」或「都不要」，可以写一句理由。

每个线程仍是普通线程：可以单独追问、审批、停止。追问之后两边不再严格同题，对比页如实标出各自多了几轮。

## 同一个起点

现在连续建两个工作树，起点可能不同：`addWorktree` 会带上当时没提交的改动，两次之间源目录可能变化。做法：

1. 从用户的目录建第一个工作树（现有逻辑，带上未提交改动）。
2. 第二个工作树从**第一个工作树**建，不从用户目录建。这时还没有 agent 动过它，内容就是起点。
3. 两个都建好后，分别记下起点快照，两个快照必须相同，否则整个创建失败并清理。

快照是一个 git 树对象，用临时索引得到，不动分支，也不动真实的暂存区：

```bash
GIT_INDEX_FILE=<临时文件> git read-tree HEAD
GIT_INDEX_FILE=<临时文件> git add -A
GIT_INDEX_FILE=<临时文件> git write-tree      # 输出树的 ID
```

它包含已提交、已暂存、未暂存和未跟踪的文件，不含被忽略的文件。比结果时在每个工作树里再取一次快照，`git diff <起点树> <结果树>` 就是完整改动，agent 中途提交过也不影响。在临时仓库里验证过：两个工作树起点树一致，结果 diff 同时包含提交、暂存和未跟踪的文件，真实暂存区不变。

## 对比页

桌面左右两栏，手机用顶部两个页签切换。从上到下：

- **任务**：发出去的原文，两栏共用。
- **概况**：实例标志和名字、模型与强度、状态、轮数、总耗时（只算实时轮次）。费用只在适配器给了数据时显示，不估算。
- **改动**：文件数和增删行数，然后是文件列表。两边都改了的文件排在前面并标出，点开看各自的 diff，复用现有的 diff 组件。
- **验证**：列出这个 agent 自己跑过的命令和结果，来自事件日志里的工具调用，标明「agent 自己跑的」。没有就写「未验证」。
- **最后的回答**：这一份的收尾文字。
- **底部操作**：用这份、都保留、都不要，加一个可选的理由输入框。

选了「用这份」之后：选中的线程照常继续；另一个归档（只停进程，记录和工作树都在，可恢复）。合并回主分支仍由用户自己做，对比页给出分支名和可复制的命令。删除工作树走现有流程，有未提交或未合并的内容时照常提醒。

## 我的选择记录

「配置」里一页，按项目列出每一次对比：任务、两个实例、选了谁、理由、日期，点了能回到对比页。顶部只写样本数，例如「这个项目共 7 次对比」，不算胜率，不排名。样本够多之前，任何比例都没有意义；以后要不要加，等用过再说。

## 数据与接口

新表 `comparisons`：

| 字段 | 含义 |
|---|---|
| `id`、`created_at` | |
| `cwd`、`task` | 用户的目录和发出的原文 |
| `base_commit`、`base_tree` | 起点的提交和快照树 |
| `candidates` | JSON 数组：线程 ID、实例 ID、模型、强度 |
| `pick` | 选中的线程 ID，或 `both` / `none`；未选为空 |
| `reason`、`picked_at` | |

线程多一个 `comparison` 字段存对比 ID，侧边栏据此归组。线程永久删除时，对比记录保留实例和任务的快照，和交接记录的做法一致。

| 接口 | 用途 |
|---|---|
| `POST /api/comparisons` | 建两个工作树和两个线程并发出任务；任何一步失败都清理干净 |
| `GET /api/comparisons` | 选择记录 |
| `GET /api/comparisons/:id` | 对比页的数据：概况、两份 diff、验证、最后的回答 |
| `POST /api/comparisons/:id/pick` | 记录选择和理由 |

| 文件 | 改动 |
|---|---|
| `packages/daemon/src/worktrees.ts` | 快照函数、树对树的 diff |
| `packages/daemon/src/comparisons.ts`（新） | 创建、汇总、记录选择 |
| `store.ts`、`http.ts` | 表、迁移、路由 |
| `packages/web/src/components/ComparePage.tsx`（新） | 对比页 |
| `Composer.tsx`、`Pickers.tsx`、`Sidebar.tsx` | 入口、第二个实例、归组 |

多机不需要额外处理：对比发生在线程所在的那台机器上，接口走现有的代理。

## 已知的坑

- **工作树里没有依赖和构建产物。** 被忽略的文件不会带过去，agent 想跑测试得先自己装依赖。这是现有工作树功能就有的问题，对比会让它更明显，所以第一版不由 hub 代跑验证命令。
- **工作树隔离不了外部资源。** 两边同时起服务会抢端口，共用的数据库会互相影响。
- **花费翻倍。** 选第二个实例时显示它的额度状况；这依赖额度档位先做好。
- **同仓库不等于同难度。** 记录说明的是「这套配置在这些任务上，用户更满意哪份」，不是模型能力。
- **测试全绿不等于需求完成，改得少不等于改得好。** 所以对比页只陈列，不下结论。

## 分期

1. **第一版**：起点快照、创建接口、侧边栏归组、对比页、选择与理由、选择记录列表。
2. **第二版，用过再定**：先选再揭晓（对比页隐藏实例名）；hub 代跑一条验证命令；让第三个实例解释两份的差异（只解释，不裁决）；已有线程「让另一个也做一遍」（需要保留每轮的起点，现在没有）。

不做：三份以上、自动合并、自动评分、个人排行榜、从普通线程日志推算指标。

## 验证

新接口要有测试，用 `test/fixtures/` 的假 agent：两个假实例各改不同的文件，断言起点树一致、两份 diff 正确、选择被记录、失败时不留工作树。界面按 `AGENTS.md` 的要求在真实浏览器里看桌面和手机、亮色和深色。
