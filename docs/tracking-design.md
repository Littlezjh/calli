# 长期跟踪设计

状态：设计稿第二版，未实现。更新：2026-10-13。

建立在[定时任务](scheduled-tasks-design.md)之上。例子：主题「炒股」，让 agent 每个交易日核对一遍关注的事，有变化才叫我。

第二版改了什么：第一版用「笔记文件变没变」判断有没有变化，Codex 成员指出这证明不了「没变化」，取数失败和 agent 漏写时文件同样不变。现在改成每次必须留一条检查记录，结果分三种。

## 先分清两件事

OpenAI 和 Anthropic 的官方材料都把长程工作分成不同的东西，我们第一版把它们混了：

| | 长期跟踪（这份设计） | 把一个目标做完（不在这份设计里） |
|---|---|---|
| 有没有终点 | 没有，一直看下去 | 有，做到验收通过 |
| 下一轮由什么触发 | 时间 | 上一轮结束且还没达到 |
| 最怕什么 | 没查到却以为没变化；打扰太多 | 过早宣布完成；原地空转 |
| 要保存什么 | 当前状态、每次查了什么 | 目标、验收条件、进度、下一步 |
| 官方的对应物 | Claude Code 的 `/loop` 和定时任务；ChatGPT 的定时任务 | Claude Code 和 Codex 的 `/goal` |

第二件事的要点记在文末，以后单独设计。

## 官方怎么说（只取和跟踪有关的）

| 来源 | 说法 | 我们怎么用 |
|---|---|---|
| [ChatGPT 定时任务文档](https://learn.chatgpt.com/docs/automations) | 提示词要写明「怎么判断有没有值得报告的事」和「什么时候停下来或问你」；先在普通对话里试，再定时；检查前几次的结果，调整提示词或频率 | 表单里这两项必填；新建后先手动跑一次建立基线，由用户看过 |
| 同上 | 独立的定时任务每次开新对话；放在对话里的定时任务沿用那个对话的上下文 | 跟踪固定用每次新线程，记忆放文件 |
| [Anthropic 的循环分类](https://claude.com/resources/articles/getting-started-with-loops) | 按时间的循环，间隔要和被盯的东西变化的频率相配 | 频率由用户按主题定，hub 不自动改 |
| [Claude Code 项目记忆](https://code.claude.com/docs/en/claude-projects) | 记忆是一组文件，每个线程开头只读索引文件，需要时再打开别的 | 状态文件和历史记录分开 |
| [LoopX](https://github.com/huangruiteng/loopx)（读过 README、三份文档和部分测试，没有运行） | 「要不要执行」和「要不要通知」是两个判断；产物没变也要写回这次的结果 | 每次都留检查记录；通知另行判断 |

以上页面主控都打开核对过。LoopX 的效果证据偏软：自己的 46 题测试里平均分高于直接用 Codex，但严格通过的题数相同，作者写明各组预算不同、不是因果结论。

## 核心决定

- **跟踪是定时任务的一种用法。** 不新增调度器，不新增页面。
- **每次都留记录，不是每次都叫人。** 检查和通知是两件事。
- **结果有三种，不是两种：** 有变化、没变化、没查全。没查全不能当成没变化悄悄收起来。
- **记忆在文件里，分两层：** 一份短的当前状态，一份只追加的历史。
- **hub 不理解内容，只读一行结果。** agent 没按格式写，就算没查全。

## 主题目录里的文件

都由 agent 维护，hub 只读，不往里写。

| 文件 | 内容 | agent 怎么用 |
|---|---|---|
| `STATE.md` | 当前状态：每个关注点现在是什么情况、上次变化是哪天。保持在一屏以内 | 每次开头读，有变化时改写 |
| `LOG.md` | 历史：每次运行追加一节，不改旧的 | 每次结尾追加，平时不用读 |

每次追加到 `LOG.md` 的一节，第一行格式固定，其余随意：

```text
## 2026-10-13 09:00
结果：有变化
查了：公司公告页、交易所披露页
结论：发布了三季度业绩预告，净利润同比增长约两成
依据：<链接>
```

「结果」只能是 `有变化`、`没变化`、`没查全` 之一。取数失败、来源打不开、只查了一部分，都写没查全并说明缺了什么。

## 用户入口

定时任务页的「新建任务」里多一个模板「跟踪一个主题」。表单：

1. **主题名**。
2. **目录**：主题自己的目录，用现有的目录选择器，可以当场新建。不用临时目录。
3. **关注什么**：标的、数据从哪里取，写到具体页面或接口。
4. **什么算变化**（必填）。
5. **什么情况先问我**（必填）：例如来源打不开超过两次、信息互相矛盾。
6. **频率、实例、权限**：定时任务原有的字段。执行模式固定为每次新线程。

hub 把这些拼成提示词，用户可以改。提交后不直接开始定时，先**立即运行一次建立基线**：agent 建好两个文件，把每个关注点的现状写进 `STATE.md`。这一次的线程留给用户看，确认 agent 理解对了，再点「开始定时」。

拼出来的提示词：

```text
你在长期跟踪一个主题：{{主题名}}。今天是 {{date}}。
先读这个目录里的 STATE.md，它是上一次留下的当前状态。
关注：{{关注什么}}
算作变化：{{什么算变化}}
先问我的情况：{{什么情况先问我}}
逐条核对，然后在 LOG.md 末尾追加一节，格式：
  ## 日期 时间
  结果：有变化 / 没变化 / 没查全（三选一）
  查了：实际查到的来源
  结论：一行
  依据：来源链接
有变化时同时更新 STATE.md。没查全时写明缺了什么。
不要下单或给出买卖承诺，不要修改这个任务的频率，不要把密钥写进文件。
```

## hub 怎么判断

一轮结束时，hub 读 `LOG.md` 里这一轮新增的部分，取「结果」那一行：

| 读到的 | 这次运行记为 | 线程 | 以后的通知 |
|---|---|---|---|
| 有变化 | 有变化 | 留在侧边栏，标未读 | 推 |
| 没变化 | 没变化 | 自动归档，运行历史里可以打开 | 不推 |
| 没查全 | 没查全 | 留在侧边栏，标「没查全」 | 第一次不推，连续出现才推 |
| 这一轮没有新增记录，或格式认不出 | 没查全 | 同上 | 同上 |
| 这一轮出错 | 失败 | 留着 | 按定时任务原有的处理 |

这样 agent 不照格式写的后果是多看一眼，不是漏掉。「结论」那一行同时存进运行历史，扫一眼列表就知道每次说了什么。

仍然会错的一种情况：agent 明明没查到却写了没变化。格式里要求写「查了」哪些来源，就是为了让这种情况在历史里看得出来；hub 不替用户核对来源。

## 没变化是常态

公告监测连续几周没有公告完全正常，不能照搬「做目标时不许空转」的规则。所以：

- 不设「连续几次没变化就提醒」。
- 任务卡片上如实显示：上次有变化是哪天、此后跑了几次、总共花了多少（实例给得出费用时）。要不要调频率由用户看着定。
- **连续 3 次失败或没查全**：自动停用，卡片标橙点并写明原因。这两种才是真的出了问题。

每次运行都会花一轮的额度，判断结果省不了这一轮。要省，得在叫 agent 之前先判断，见分期里的探测命令。

## 权限

- 「只读外面、只写这两个文件」只是提示词里的要求，不是权限边界。选了完全访问，它就是一个没人看着、能联网、能执行命令的 agent。表单里照实写这句话。
- 选「请求批准」，agent 每次要联网取数都会停下来等。没有手机通知之前，等于每次都卡住。
- 建议主题目录里只放这两个文件。目录隔离不是沙箱。

## 和标签、看板的关系

- 跟踪任务可以贴标签（见[看板与标签](board-tags-design.md)），它建出的线程带上同样的标签。
- 看板上这些线程带「定时」徽标；有变化和没查全的落在「待处理」列，卡片上写明是哪一种。
- 不和计划项绑定。

## 炒股这个例子

agent 适合做的：按用户写下的条件定期核对，附来源，记下来。取数最好写成固定的命令或地址，比依赖各家 agent 参差的联网工具稳。

不该让它做的：下单；给出买卖承诺；预测；为了显得有用每次都报有变化。实时行情也不适合：定时的粒度是分钟，一轮本身要跑几十秒到几分钟。

## 数据与接口

不加新表、新路由，只加字段：

| 位置 | 字段 | 含义 |
|---|---|---|
| `schedules` | `tracking` | 是否是跟踪任务；是的话按上面的规则读 `LOG.md` |
| `schedule_runs` | `outcome` | 有变化、没变化、没查全；非跟踪任务为空 |
| `schedule_runs` | `summary` | 「结论」那一行，最多 200 字 |
| `GET /api/schedules` 的每一项 | `lastChangedAt`、`runsSinceChange`、`troubleStreak` | 从运行历史算出 |

| 文件 | 改动 |
|---|---|
| `packages/daemon/src/scheduler.ts` | 一轮结束后读 `LOG.md` 新增部分、记结果、没变化时归档、连续出问题时停用 |
| `store.ts` | 字段和迁移 |
| 定时任务的表单（前端还没做） | 模板、先跑一次基线再开始定时 |

读 `LOG.md` 走线程目录的只读文件检查，和文件查看器同一套。

## 分期

1. **第一版**：模板和基线、两个文件的约定、三种结果、没变化自动归档、运行历史里的结论、连续出问题自动停用。
2. **第二版，用过再定**：探测命令。用户给一条取数命令，hub 到点先跑它并对输出算哈希，没变就不叫 agent，这一轮的额度也省了；命令失败记为没查全。
3. **等别的功能**：推到手机（等通知方案）；额度用完时的明确提示（等 `rate_limited` 错误码）。

不做：agent 自己改频率、agent 下单、固定线程累积上下文的跟踪（压缩能力各家不齐，Antigravity 和 TRAE 没有）、hub 替用户核对来源、跨机器汇总。

## 验证

用 `test/fixtures/` 的假 agent 覆盖五行判断表各一条；连续三次没查全后任务被停用；`LOG.md` 不存在、格式不对、只改了 `STATE.md` 没追加记录，都落到没查全。界面按 `AGENTS.md` 的要求在真实浏览器里看。

## 不在这份设计里：把一个目标做完

这是另一个功能，这里只记下官方材料里反复出现的要素，以后单独设计。

- **可验证的完成条件。** Claude Code 的 [`/goal`](https://code.claude.com/docs/en/goal) 要求一个可度量的终态和证明方式；Codex 的 [Goals 说明](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)写的是不能因为模型觉得大概做完了就算完成，要对照文件、测试、日志。
- **验收者不是干活的那个。** Claude Code 每轮结束由另一个小模型判断达没达到。Anthropic 的[文章](https://www.anthropic.com/engineering/harness-design-long-running-apps)说 agent 给自己的活打分稳定地偏乐观。
- **进度落在文件里。** Anthropic 的[另一篇](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)用功能清单（每项带通过标记）、进度日志和小步提交；每个会话开头读它们，结尾写回。
- **预算和防空转。** Codex：预算用完不等于完成，要停下来总结进展和阻塞；一轮没有任何工具调用，下一次自动继续就被抑制。Claude Code：连续几轮没有动作就把控制权还给用户。
- **出错要分类。** Claude Code：限流和额度用完是暂停，等恢复后继续；凭据失效这类直接清掉目标等用户处理。

Calli 最小的做法大概是：有原生目标模式的 agent 通过适配器接出来，hub 只显示状态，不另起一个循环去驱动同一个线程；验收者可以选另一家的实例，这是别家产品给不了的。Claude 的 `/goal` 在我们的接入方式下能不能用，还没有验证。
