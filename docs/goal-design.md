# 目标设计

状态：设计稿第二版，未实现。更新：2026-10-13。

给线程一个目标，agent 一轮接一轮做下去，直到做完、被卡住或预算用完。和[长期跟踪](tracking-design.md)是两件事：跟踪没有终点，按时间触发；目标有终点，上一轮结束且还没做完就接着做。

第二版改了什么：Codex 和 Antigravity 两位成员评审了第一版（原定的 pi 因额度用完没能参加）。主要改动是续轮改为统一排队、防空转规则收窄、计划文件由 hub 建骨架并按目标分开、原生目标的互斥放进第一版、上下文快满时有出路。

## 核心决定

- **目标属于 hub，不属于某个 agent。** 目标、完成条件、预算和状态存在 hub。没有目标模式的 agent 也能用；额度用完换一个 agent 时目标跟着走。
- **第一版一律由 hub 驱动。** 行为一致，只需要测一套。agent 自带的目标模式第二版再接，但「不能两套循环同时驱动一个线程」第一版就要保证。
- **拆解是 agent 的事，记在文件里。** hub 不拆任务，只读清单的勾选情况。
- **不安装技能。** 做法写成一小段说明，由 hub 附在目标轮次里，和协作功能同一个做法。
- **agent 说做完不算完成。** 包括 agent 自带目标模式判的「完成」。都要用户确认。

## 各家现状

| Agent | 自带目标模式 | 接入原生模式的难度 |
|---|---|---|
| Codex | 有。`codex app-server` 0.160.1 的协议里有 `thread/goal/set`、`get`、`clear` 和 `thread/goal/updated` 通知，六种状态，带 token 预算（生成协议定义核对过，没有实际调用） | 大。适配器现在只认 hub 发起的轮次（`adapters/codex.ts` 的 `prompt()`），原生目标自己续的轮次会被忽略，审批会被默认取消。要有常驻的事件通道、两边轮次的对应、审批和取消的整合 |
| Claude Code | 有 `/goal`，每轮结束由另一个小模型判断 | 未知。它是会话内的钩子，经 ACP 接入时能不能用没有验证 |
| pi、Antigravity、TRAE | 没有查到 | 不适用 |

## 用户入口

1. 斜杠面板里的 `/goal`（hub 自己提供的命令，和 `/status` 同一层），或线程菜单「设为目标」。
2. 填三样：**目标**、**完成条件**（怎么算做完，最好能检查：测试通过、文件存在、清单清空）、**最多几轮**。目录是 git 仓库时可选「在新工作树里做」，默认勾上。
3. 开始后，输入框上方一条目标状态：目标的第一行、进度（已完成 3 / 8）、已用轮数，以及暂停、继续、清除。
4. 需要用户的状态出现时，线程进看板的「待处理」列，卡片写明是哪一种。

轮数上限的默认值看适配器能力：有压缩能力的默认 20，没有的默认 8。前端读能力，不认 agent 名字。

## 计划文件

位置 `.calli/goals/<目标 ID>.md`，每个目标一个文件，同一目录里的两个目标互不覆盖。设置目标时 hub 建好骨架：

```text
# 目标
{{目标}}

# 完成条件
{{完成条件}}

# 清单

# 进展
```

之后由 agent 填清单、勾选、追加进展，hub 只读。目录是 git 仓库时，hub 把 `/.calli/` 写进 `.git/info/exclude`，和 `.worktrees/` 同一个做法。

hub 驱动的每一轮，输入末尾附一段说明（界面上隐藏）：

```text
<calli-goal>
你在朝一个目标工作，计划文件：.calli/goals/{{目标 ID}}.md，先读它。
清单是空的：把目标拆成几项，每项一行，以「- [ ] 」开头，写明这一项怎么验证。这一轮只拆，不动手。
清单不空：只做第一个没勾的项。做完并验证过，把它改成「- [x] 」，在「进展」下追加一行，写你跑了什么检查、结果是什么。
需要我决定才能继续：在「进展」下写一行「阻塞：原因」，然后停下。
全部勾完后停下。不要自己宣布目标完成，由我验收。
</calli-goal>
```

这段说明就是「目标技能」的全部内容。Antigravity 成员的判断是每轮附说明比装技能更稳：技能要 agent 主动调用，容易漏。

agent 不会完全照做，评审里预计最常见的两种走样：一轮把所有项做完并全部打勾；勾了但没有真的验证。前一种不拦，结果直接进验收；后一种靠「进展」里那一行检查记录让用户在验收时看得出来。

## 续轮怎么排队

续轮不在「一轮结束」的那一刻发。现在一轮结束的顺序是先发结束事件，再释放运行锁，再发排队的消息；目标如果一听到结束就发下一轮，会和用户的消息、协作的投递抢。做法：

- 线程收尾完成后，由一处统一决定下一轮是谁，顺序固定：**用户排队的消息，然后协作投递，最后才是目标续轮。**
- 决定续轮之前读计划文件；读完再检查一次目标有没有被暂停、清除或改过，队列里有没有新消息，有就放弃这次续轮。
- 停止、清除、归档、交接，都撤销还没发出的续轮。用户点「立即发送」打断当前这轮不算暂停目标。

## 什么时候续，什么时候停

只有 hub 发起的目标轮次参与下面的判断。用户自己发的问答、`/usage` 这类命令不算轮数，也不触发防空转。

线程收尾后，按顺序判断，命中第一条就停：

| 情况 | 状态变成 | 说明 |
|---|---|---|
| 用户按了停止 | 已暂停 | 等用户点继续 |
| 有审批没处理，或有用户消息、协作投递在排队 | 不变 | 不续，等它们处理完 |
| 这是协作的主控线程，且有成员在跑或有结果没送达 | 不变 | 等成员是正常的，不算空转 |
| 这个会话在终端里被用过（现有的终端同步能发现） | 已暂停 | 可能有别的东西在驱动它，见「互斥」 |
| 这一轮出错，原因是额度或限流 | 额度用完 | 提示交接；显示重置时间（报错里有的话） |
| 这一轮出错，其他原因 | 第一次重试，再错就已暂停 | 重试也算一轮 |
| 「进展」里新出现「阻塞：」 | 被卡住 | 显示原因，用户回话后继续 |
| 清单至少有一项，且全部勾完 | 等你验收 | 空文件、没有清单、格式认不出，都不算勾完 |
| 已用轮数到上限 | 预算用完 | 发出每一轮之前先检查并记数；预算用完不等于完成 |
| 上下文占用超过七成 | 有压缩能力：先压缩再续。没有：上下文快满 | 后者提示「在新线程里接着做」，目标和计划文件跟过去 |
| 连续两轮既没有工具调用、计划文件也没变 | 已暂停 | 写明「两轮没有进展」 |
| 以上都不是 | 进行中 | 发下一轮：一句「继续」加上面的说明 |

防空转从第一版的两条收成一条。原来「一轮没有工具调用就停」会误伤 agent 用文字说明风险的情况；「两轮计划没变就停」会误伤一项要做好几轮的大任务。两个条件同时成立才算空转。

不上报上下文占用、又没有压缩能力的 agent（现在是 Antigravity），只能靠较低的轮数上限兜底。

daemon 重启后目标一律变成已暂停，不自动续跑。

## 互斥

一个线程只能有一个东西在推它往前走。

- **成员线程不能设目标；已有目标的线程不能成为协作成员。** 两个方向都校验。
- **定时任务的线程不能设目标。**
- **Codex**：设置 hub 目标之前，适配器用 `thread/goal/get` 查一次。会话里已有活动的原生目标就拒绝，并说明原因；不替用户清掉它。查不了（旧版本、调用失败）也拒绝。
- **Claude Code 和其他**：查不了原生状态。靠现有的终端同步：发现这个会话在终端里被用过，目标就暂停，由用户决定继续还是清除。

## 状态

| 状态 | 含义 |
|---|---|
| 进行中 | 会自动发下一轮 |
| 已暂停 | 用户停的，或者防空转、重启、终端里用过 |
| 被卡住 | agent 写了阻塞原因。可能在等用户，也可能在等外部条件，所以不叫「等你决定」 |
| 额度用完 | |
| 预算用完 | 轮数到上限 |
| 上下文快满 | 只出现在没有压缩能力的 agent 上 |
| 等你验收 | 清单勾完 |
| 已完成 | 用户确认之后 |

执行状态和验收分开存。第二版接 Codex 原生目标时，它的 `complete` 映射成「等你验收」，不直接算已完成；它的 `blocked`、`usageLimited`、`budgetLimited`、`paused` 对应同名的四种。

## 验收

- **第一版：用户验收。** 用户看改动和「进展」里的检查记录，点「完成」，或者写哪里不行。在工作树里做的话，用[同题对比](compare-design.md)那套起点快照给出完整 diff。
- **写了反馈之后**：状态回到进行中，反馈作为下一轮的输入，并要求 agent 把相关的项改回未勾或加新项。计划文件发生变化之前，不会再次进入「等你验收」，免得原样又报一次完成。
- **第二版：另一个实例验收。** 在同一目录开一个验收线程，默认选不同厂商的实例；让它自己读文件、跑检查，不采信对方的说法；结论写进 `.calli/goals/<目标 ID>.review.md` 的第一行（通过、不通过、无法判断）。不通过把意见发回去继续，最多三轮；无法判断或格式认不出就停下等用户。

## 权限和隔离

- 目标是无人值守的多轮工作：请求批准会卡住，完全访问就是没人看着。表单里照实写。
- 默认在新工作树里做，不满意可以整个丢掉。
- 轮数上限必填。

## 和其他功能的关系

- **交接**：额度用完或上下文快满时交接，目标和计划文件留在原目录，接手线程带着同一个目标继续；原线程的目标先停。
- **看板**：卡片显示进度和状态；被卡住、等你验收、预算用完、额度用完、上下文快满都在「待处理」列。
- **计划页**：计划项可以关联目标线程；不自动勾选计划项。

## 数据与接口

线程多一个 `goal` 字段（JSON）：目标 ID、目标、完成条件、执行状态、状态原因、是否已验收、轮数上限、已用轮数、进度（已勾和总数）、版本号、开始时间。版本号在每次用户修改时加一，续轮发出前比对。不建新表。

| 接口 | 用途 |
|---|---|
| `PUT /api/threads/:id/goal` | 设置目标、建计划文件骨架、开始第一轮 |
| `POST /api/threads/:id/goal` | `action`：暂停、继续、完成、反馈、清除、加轮数 |

每次状态变化在事件日志里记一条，线程里显示成一行。

| 文件 | 改动 |
|---|---|
| `packages/daemon/src/goals.ts`（新） | 判断表、读计划文件、状态 |
| `threads.ts` | 收尾后的统一排序（用户消息、协作投递、目标续轮）；目标轮次附说明；重启时暂停 |
| `coordination.ts` | 把投递并进统一排序；成员和目标的互斥 |
| `store.ts`、`http.ts` | 字段、迁移、两个接口 |
| `adapters/codex.ts` | 查询原生目标是否存在 |
| 前端 | `/goal`、表单、输入框上方的状态条 |

改动最重的是 `threads.ts` 里的统一排序：它动的是现有的排队和协作投递路径，不是新增一块独立的东西。

## 分期

1. **第一版**：hub 驱动、计划文件、统一排序、判断表、互斥、用户验收、状态条。
2. **第二版**：另一个实例验收；额度用完或上下文快满时一键带着目标换线程；Codex 原生目标经适配器接入。
3. **用过再定**：token 和时间预算；把清单显示在线程里。

不做：hub 替 agent 拆任务、多个 agent 认领同一个目标、目标之间的依赖、自动合并改动、每轮都开新会话（Antigravity 成员指出这会丢掉上一轮摸清的东西，每轮重读仓库）。

## 没有验证的

- Codex 的 `thread/goal/*` 只核对了协议定义，没有实际调用。
- Claude Code 的 `/goal` 经 ACP 能不能用。
- 各家 agent 会不会照着维护计划文件。这是最大的假设。评审里两位成员都认为不会完全照做，判断表里的「至少一项且全部勾完」「两轮没有进展」和用户验收就是为它兜底的。
- 「额度或限流」的识别依赖 `rate_limited` 错误码，这个码还没有。没有之前，这类错误落到「其他原因」，表现为重试一次后暂停。

## 验证

用 `test/fixtures/` 的假 agent 覆盖判断表的每一行；用户消息和协作投递排在续轮前面；暂停、清除、归档后没有续轮发出；重启后目标暂停；计划文件为空、没有清单、格式不对时不进验收。界面按 `AGENTS.md` 的要求在真实浏览器里看。
