# 成员信箱：传话不进对话流

成员（子 agent）给入口成员（主 agent）的交回，是 agent 之间的私下信件，不是用户发言。对齐 Claude Code / Codex 的共同原则：子 agent 的输出不作为对话展示给用户——Claude Code 的传话走工具通道（可折叠机器行），主 agent 决定转述什么；Codex 的子 agent 只回摘要，原始过程在 `/subagents` 按需看。用户需要的是三样：状态一眼可见、决策点浮出、想看时有点开的入口。

## 之前的做法（为什么吵）

`pump()` 把每一封投递 `startTurn` 成主线程的一整轮。成员每交回一次，主线程就多一整轮（信件卡 + 工作块 + 主 agent 的一段话）；人和主 agent 聊着聊着，成员交回插进来，主 agent 再回它，用户自己的对话线被冲走。

## 现在：信箱

结果信件（`kind: 'result'`）到入口线程（`t.rootId`）时不再各自开轮：

| 信件内容 | 行为 |
|---|---|
| 成员写了 `[进度] 进行中` / `等外部` | 静默：留在信箱，不叫醒；随主 agent 下一次开口作为只读上下文捎带（`mailboxNotice`，读一次就消费），不重复 |
| `[进度] 待验收` / `需要你` / 失败 / 没写 `[进度]`（保守回退） | 叫醒：把信箱里**积压的全部信件并成一轮**投给主 agent（`deliverMailbox`），不是一封一轮 |

- 信件开头的一行状态按成员自己的 `[进度]` 改写：`进行中通报（无需回应）` / `本轮已返回，仍需验收` / `失败`。
- 合并轮的输入就是信件原文本身，各带原有 `[协作消息｜…]` / `[团队消息｜…]` 头，一封一封排下来，不加任何包裹文字（协议对齐靠信件头，agent 的应答锚在信件内容上）；「多封并一轮、需要拍板的才对用户说」写进主 agent 常驻的协作说明块，不随信件走。`displayText` 是「来自 A、B 的结果」，界面仍是一张交回卡。
- **人优先不变**：主线程有排队的人消息或正在运行时，信件不投（原有 guard）；人的那轮先走，信件等它结束后再批量投。
- 成员之间的往来（工作链）不变，仍按消息逐封开轮——那发生在成员线程，不进主时间线。
- 团队任务里，静默信件不挡 `awaiting_confirm`（`complete()` 不再把它算作待办）。
- 重启恢复的信件带上同样的叫醒标记。
- **成员侧协议语义**（2026-11-20 补）：全局 `<calli-progress>` 把「待验收」教成「做完请检查」，成员的收尾确认（「收到、已知悉」）据此标了待验收，照样叫醒主控——引擎按协议行事，错在语义冲突。协作和团队的成员说明里各加一句覆盖：只有带新成果、需要人验收的交回才写 `待验收`；纯确认、收尾、没有新东西写 `进行中`（静默进信箱）。主控说明不含这句。

## 数据

`Delivery` 增加三个标记（随投递记录持久化，消息页可见）：

- `wake`：这封信要不要叫醒入口（入队时按成员 `[进度]` 判定）。
- `picked`：信箱批量正在尝试为它开轮，注入上下文时跳过。
- `noticed`：已随主 agent 某轮作为上下文送达，不再重复。

## 界面（保持不变的部分）

交回卡（`DeliveredNote`）照旧：合并轮显示「来自 A、B 的结果」，状态取最后一封信的 `[进度]`。静默信件不在时间线加行——成员状态仍从侧栏成员行和线程概况看（`coordination.doing`）。后续若要做主线程里的一行「进行中状态条」（就地更新），另起设计。

## 参考

- Claude Code 后台 agent：完成是发给主 agent 的通知，合并进下一个轮次，主 agent 决定转述什么（"relay what matters"）。
- Codex subagents：子 agent 只回摘要给 lead，`/subagents` 按需查看原始线程。
- GitHub 时间线：人的评论与机器事件分型渲染；Chatwoot：内部协作不进对外时间线。
